# NexusDesk 12 周开发周期与求职计划

**个人执行版项目计划**  
版本：v1.0｜制定日期：2026-11-09  
适用对象：计算机科班本硕、研二，了解 Go / Gin / 数据库，可独立写基础接口，目标是 Go 后端或 AI 应用后端岗位

> 时间是假设，不是交付承诺：以每周 12～18 小时为基础，12 周约 144～216 小时。论文、课程、实习申请等事务优先时，可以延长周期；绝不以赶进度为由跳过关键验收。

## 1. 计划目标与实施原则

### 1.1 12 周内形成的作品

- 具备真实业务功能的 Web 产品，允许两个角色完成工单创建、处理和知识问答。
- 完整可复现的 Go + PostgreSQL + Redis + Vue + Docker 技术栈。
- 至少两个能够深入讲解并展示代码和测试证据的重点模块，建议“工单并发与事务”和“异步文档处理 + RAG”。
- 能使用 Codex 完成有限范围开发、代码审查、测试补全、分析故障，同时坚持自己验收。
- 求职交付物：可公开仓库、演示视频、架构与数据库设计、测试/性能报告、简历条目和面试问答材料。

### 1.2 工时分配建议

| 活动 | 每周建议时长 | 目标 |
| --- | --- | --- |
| 自己写代码与调试 | 6～8 小时 | 核心功能亲自实现 |
| 官方文档与原理学习 | 2～3 小时 | 理解关键技术 |
| ChatGPT/Codex 协作 | 2～3 小时 | 设计审查、测试、Review |
| 测试、记录与复盘 | 2～4 小时 | 可验证的开发成果 |

不强制每天学习相同时间。尽量保持每周至少 3 次实际编码和 1 次功能演示；每个任务结束前至少提交一次有意义的 Git Commit。

### 1.3 三条不能牺牲的约束

1. **可运行优先。** 每周末仓库应处于可安装、可启动或可回退状态，不允许连续几周只有设计和依赖配置。
2. **掌握优先。** 关键并发、SQL、权限、异步流程先自己完成；AI 生成代码须人工理解与验证。
3. **求职优先。** 功能过多时优先保留可展示业务、技术难点和真实测试结果，主动舍弃炫技功能。

## 2. 依赖关系与关键里程碑

```text
W1 需求/环境/基础架构
  -> W2 用户组织与权限
  -> W3 工单 CRUD + 数据库事务
  -> W4 UI 联调 + 并发领取验证        [G1 业务 MVP]
  -> W5 文件上传/存储
  -> W6 Embedding/向量检索/RAG
  -> W7 Asynq/Worker/幂等重试
  -> W8 SSE/安全工具调用             [G2 AI MVP]
  -> W9 缓存、限流、复杂 SQL
  -> W10 检索评测、Agent/MCP 选做
  -> W11 压测、pprof、日志与观测
  -> W12 部署、文档、演示、面试复盘    [G3 求职版]
```

**关键路径：** 身份与租户权限 -> 工单数据模型 -> 核心业务可运行 -> 文档摄取 -> RAG -> 工具调用 -> 测试证据。MCP、Kafka、微服务和 Kubernetes 都不是关键路径，不应妨碍 G1/G2。

## 3. 逐周执行清单

### 第 1 周：需求冻结与工程启动

**学习重点：** Go Modules、配置读取、目录职责、HTTP API 约定、SQL migration、Git 分支与审查流程。

**亲自完成：** 用自己的语言写 3 个用户故事；确定 P0 范围；画出前端、API、DB 的关系；初始化 Go/Gin；创建健康检查接口；创建第一个 migration。

**AI 协助：** ChatGPT 指出 PRD 遗漏与架构风险；Codex 只读审查目录和配置；允许 Codex 生成基础 `.gitignore`、Makefile 草案，但自己核对。

**交付：** `docs/requirements.md`、`docs/architecture.md`、`AGENTS.md`、`GET /healthz`、Docker Compose 中 PostgreSQL 可以启动。

**验收：** 新机器按 README 可启动 Go 服务；所有配置来自环境变量；`go test ./...`、`go build ./...` 可以执行。

### 第 2 周：认证、组织与权限

**学习重点：** 密码安全散列、JWT 校验、Gin 中间件、RBAC 与对象级授权。

**亲自完成：** `users / organizations / organization_members` 的 migration；注册、登录、当前用户接口；中间件解析用户身份；组织成员关系校验。

**AI 协助：** 审查 token 校验、权限设计、错误响应；为无权访问和 token 失效补充测试。

**交付：** 登录接口、成员与组织数据、认证集成测试、权限矩阵。

**验收：** 未登录不能访问受保护 API；用户 A 不能假冒组织 B；不在日志中打印密码、token 或密钥。

### 第 3 周：工单 CRUD、状态机与事务

**学习重点：** pgx、SQL 事务、约束与索引、Service 与 Repository 分工。

**亲自完成：** 工单/评论/事件表；工单 CRUD、分页、状态变更；在一次事务中写入工单状态和操作事件。

**AI 协助：** 审查 SQL、命名与错误分类；指出状态机边界条件；不允许 AI 代写完整核心 Service。

**交付：** 可通过 API 测试完整工单流程；状态机规则文档。

**验收：** 非法状态转换被拒绝，事务失败不产生半成品数据，组织之间不能互相访问工单。

### 第 4 周：前端联调与并发领取（G1）

**学习重点：** 端到端 HTTP 调用、并发条件更新、乐观锁/事务隔离、`go test -race` 适用边界。

**亲自完成：** 工单领取接口和并发测试；后端错误码映射；前端能登录、建单、查看、领取与处理工单。

**AI 协助：** Codex 可以生成基础 Vue UI 和表单样式；对并发测试进行 Review；自己判断实现是否确实保证并发安全。

**交付：** G1 业务 MVP、最简演示视频（1～2 分钟）、演示数据。

**验收：** 同一工单两名用户同时领取，最终只能有一个有效领取人；演示端到端业务；Docker 环境可启动。

### 第 5 周：文件上传与知识库基础

**学习重点：** multipart 上传、文件流、存储抽象、校验和、文件安全。

**亲自完成：** `documents` 表、上传 API、文件元数据、文件列表与删除状态；本地存储适配层。

**AI 协助：** 审查路径穿越、MIME 校验、文件大小限制、资源泄露等；辅助生成恶意文件名测试。

**交付：** 上传 TXT/Markdown/文本型 PDF，后台可以读取并展示文档信息。

**验收：** 组织 A 无权下载组织 B 的文档；非法格式及超限文件得到明确错误；存储目录不暴露在公共路由下。

### 第 6 周：RAG 最小版

**学习重点：** Embedding、Chunk、向量相似度、pgvector、引用来源与评测基线。

**亲自完成：** 文档解析和分段（先可同步，仅用于建立基线）；向量生成与写入；组织范围内相似度查询；最小带引用问答。

**AI 协助：** 帮助理解距离算子与索引选择；审查 Embedding 接口边界；辅助构造评测问题，不代替人工标注参考答案。

**交付：** 单文档/多文档 RAG 演示；至少 20 道初始评测问答集。

**验收：** 回答可定位到真实来源；无相关材料时能说明不足；不同组织检索彼此隔离。

### 第 7 周：异步任务与可靠性

**学习重点：** Goroutine/Channel/Context、Asynq、Worker Pool、重试与幂等。

**亲自完成：** `cmd/worker`、任务状态表、解析任务排队与执行、重试规则；为重复投递设计去重/幂等；模拟崩溃和重新执行。

**AI 协助：** 审查死锁、取消传播、重复写入与退出条件；可让 Codex 编写故障注入脚本并报告实际运行结果。

**交付：** 文件上传快速返回任务 ID；处理状态可查；Worker 重启后任务不会产生重复业务结果。

**验收：** 同一文档重复任务不会产生重复 Chunk；失败原因可追踪；任务重试遵循明确次数与退避规则。

### 第 8 周：SSE 与安全工具调用（G2）

**学习重点：** SSE、流式取消、原生 Function Calling、工具 schema 与审批。

**亲自完成：** 聊天流式接口；知识库搜索工具、查询工单工具；创建工单需用户确认的最小工具工作流。

**AI 协助：** Codex 生成 EventSource/Fetch Stream 前端基础代码；审查确认逻辑和工具参数校验。

**交付：** 用户可提问、查看引用、请求 Agent 提议创建工单并手动确认。

**验收：** 非法工具参数无法执行；无确认不能创建新工单；断连能够取消不必要的模型请求；外部模型故障不影响工单业务。

### 第 9 周：缓存、限流与稳定性

**学习重点：** Redis 缓存策略、缓存击穿、热点读取、令牌桶/固定窗口、数据库查询分析。

**亲自完成：** 选择一个有证据的热点读场景加入缓存；增加登录/AI/上传限流；用 `EXPLAIN ANALYZE` 优化至少一个 SQL 查询。

**AI 协助：** 分析负载与实验设计；提出缓存失效风险；由你决定是否采用优化建议。

**交付：** 缓存方案记录、限流测试、SQL 前后对比报告。

**验收：** 未命中/过期/Redis 不可用有可解释的行为；不存在跨租户缓存泄漏；优化结论基于实测。

### 第 10 周：AI 工程增强与评测

**学习重点：** Recall@K、MRR、混合检索、模型错误分类、Agent/MCP 边界。

**亲自完成：** 扩充评测集至 50～100 条；比较精确向量检索与备选方案；记录 Token 成本和延迟；修正引用质量。

**AI 协助：** 可以借助 Eino 或 MCP SDK 进行小范围探索，但不能让探索抢占核心评测。Codex 可生成对比实验脚本，评价标准由你制定。

**交付：** `docs/rag-evaluation.md`、实验数据、可重跑脚本；MCP 为选做项。

**验收：** 明确实验语料、检索参数、模型版本、指标定义；对无答案和跨租户问题做负向验证。

### 第 11 周：压测、故障演练与可观测性

**学习重点：** pprof、Go 内存分配与 GC、指标、追踪、日志关联 ID、压测方法。

**亲自完成：** 业务 API 压测；分析一个真实 CPU/内存或 SQL 瓶颈；对 Worker、Redis/DB 短时不可用做演练；记录优化前后证据。

**AI 协助：** 帮助读火焰图或 profile、形成待验证假设；不得把 AI 的假设写成已证实结论。

**交付：** `docs/performance-report.md`、`docs/failure-drills.md`、最少一份 pprof 记录。

**验收：** 性能数据写明机器、数据量、并发、测试工具与测试时间；区分纯业务 API 和 LLM 请求。

### 第 12 周：交付求职作品（G3）

**学习重点：** 维护性、文档写作、技术叙述、Demo 与面试复盘。

**亲自完成：** 清理仓库、核对测试、完善 README、录制 5～8 分钟 Demo、准备项目简历描述和 10 个深入面试问题。

**AI 协助：** 审查文档、模拟面试、检查简历陈述是否与真实证据一致；Codex 只做明确的收尾修复。

**交付：** GitHub 公共仓库、项目演示、架构图、API/DB 设计、评测和性能报告、简历一版。

**验收：** 新用户按 README 能复现关键场景；你不依赖 AI 可以演示并解释两项技术难点。

## 4. 第一周每日任务（可直接执行）

| 日期 | 推荐投入 | 自己完成 | AI 协助与完成定义 |
| --- | --- | --- | --- |
| D1 | 2 h | 写 3 个故事与 P0 列表 | ChatGPT 挑遗漏；冻结 P0 范围 |
| D2 | 2 h | 画实体关系、列出表和权限 | AI 讨论索引与约束，输出草案 |
| D3 | 2 h | 初始化 Go、Gin、Git | Codex 只读审查；服务可启动 |
| D4 | 2 h | 连接 PostgreSQL、首个迁移 | AI 讲解迁移与事务；表可创建 |
| D5 | 2 h | 健康检查、统一错误响应 | AI Review；`go test ./...` 通过 |
| D6 | 1～2 h | Compose、配置和 README | Codex 辅助部署；本地能复现 |
| D7 | 1～2 h | 复盘、录制演示、整理 Commit | AI 模拟提问；回答基础架构选择 |

如果 W1 任务没有按期完成，优先推迟 UI 美化和 AI 扩展，不减少认证和数据隔离验证。

## 5. 每周固定工作节奏

### 5.1 开发前 15～20 分钟

- 阅读上周复盘与本周目标，明确一个可完成的小任务。
- 用自己的话写出输入、输出、边界条件、验收方式。
- 确定 AI 模式是“讲解”“审查”还是“限范围实现”，避免任务混杂。

### 5.2 编码时

每个任务以“个人设计 -> AI 审查 -> 个人实现 -> 测试 -> Codex Review -> 个人修复 -> 提交”为基础。对 UI、模板和测试基础设施可放宽 AI 生成比例，但仍需人工验收。

### 5.3 周末复盘（30～45 分钟）

写下：本周完成的可运行功能、遇到的真实 Bug、独立解决的部分、AI 介入点、测试证据、尚未理解的知识点、下周变更需求。录制 60 秒功能演示或保存测试输出。

## 6. 进度看板与完成定义

任务状态建议：`Backlog -> Ready -> In Progress -> Review -> Verified -> Done`。只有通过验收标准和相关测试才能进入 Done；AI 自称“已完成”不能替代状态迁移。

| 看板字段 | 含义 |
| --- | --- |
| 任务 ID / 优先级 | 如 `W03-T02 / P0` |
| 用户故事 | 解决什么业务问题 |
| 负责者 | 你负责最终决策与验收 |
| AI 参与模式 | 讲解 / 只读审查 / 测试 / 限范围实现 |
| 验收标准 | 可观察的结果与错误处理要求 |
| 证据 | Commit、测试、日志、截图、benchmark |
| 技术收获 | 自己能解释并复现的原理 |

**Definition of Done（DoD）：** 业务行为符合需求；错误场景验证；代码格式和测试通过；权限检查完成；文档同步；无密钥泄漏；代码 Review 完成；本人能够独立解释核心实现。

## 7. 困难分级与减配策略

### 7.1 遇到问题时的时间盒

- 小型编译/接口错误：先独立查日志、最小复现和官方文档约 20～30 分钟，再找 AI。
- 复杂并发/事务 Bug：先花约 45～60 分钟收集证据，必要时更早请 AI 帮忙提出排查假设，但由自己验证。
- 外部 SDK 兼容性或部署阻塞：优先让 AI 帮助检索官方文档和构造最小复现，避免盲试。

以上是建议而非硬性计时，重点是保留独立分析的机会，也避免无效卡住几天。

### 7.2 如果只剩 8 周

保留 W1～W8 中 P0/P1 的核心，舍弃可观测系统全家桶、MCP、复杂多 Agent、Kubernetes、Kafka 和高级统计看板。至少完成工单并发控制、文档异步处理、RAG 最小版和完整演示。

### 7.3 如果论文或秋招突然占用时间

每周维持一个可验证任务，优先处理现有 Bug 与文档，暂停新增功能。维护 `NEXT.md`，记录下一次回来时只需执行的第一步。不要为了追赶计划让 AI 批量生成未经理解的核心模块。

## 8. 求职准备同步进行

| 时间 | 求职输出 | 技术深挖角度 |
| --- | --- | --- |
| W4 | 第一版项目介绍（事实版） | Gin 分层、认证、事务、并发领取 |
| W8 | 演示视频和架构图 | Go Worker、消息重试、RAG、Tool Calling |
| W10 | AI 系统评测报告 | 召回指标、引用质量、成本、权限 |
| W11 | 性能优化报告 | pprof、SQL、Redis、P95 延迟 |
| W12 | 正式简历与面试题 | 为什么这样设计、替代方案、失败经验 |

建议选定两项“个人招牌技术故事”，每项准备五部分：背景、约束、第一版方案、遇到的失败、改进与实测证据。不要写未完成的功能和未经测试的提升百分比。

## 9. 可量化的个人成长指标

- 每周至少有 1 个可运行成果、1 条经过验证的技术结论、1 次 Git 审查记录。
- 关键模块的核心 Service 能脱离 AI 阅读并修改；每两周做一次闭卷式代码讲解。
- 至少完成 2 次“自己复现 -> 自己定位或提出假设 -> AI 协助 -> 自己验证”的故障记录。
- 完成 1 份并发正确性证明材料、1 份异步重试/幂等测试、1 份检索评测报告、1 份性能实验。
- 保留 Codex 任务描述、修改差异、测试输出及人工修正记录，以证明 AI 协作能力。

## 10. 每个里程碑的 Go / No-Go 决策

**G1（W4）：** 工单业务与租户隔离不能稳定运行，停止开发 AI 模块，优先修复。

**G2（W8）：** 无法证明文档处理幂等或 Agent 写操作需要确认，停止开放相关演示入口，先解决安全与可靠性问题。

**G3（W12）：** 若高阶模块不完整，展示已通过测试的可靠功能，不展示半成品；如实注明后续计划。
