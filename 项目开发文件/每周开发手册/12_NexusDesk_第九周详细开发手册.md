# NexusDesk 第九周详细开发手册
## 主题：Redis 缓存、接口限流与 PostgreSQL 查询优化

**建议周期：** 7 天，约 12–18 小时。若课程或科研任务较多，可以延长，不要为了赶进度跳过测试。  
**本周定位：** 在第八周已经完成 SSE、受控 Function Calling 和人工确认的基础上，优化系统的读取性能与资源使用，并建立可验证的限流保护。

---

## 一、本周目标

完成本周后，你应该能够：

1. 说清楚 NexusDesk 哪些数据适合缓存，哪些数据不能缓存。
2. 为知识库列表、工单列表等读多写少的数据实现 Redis 缓存。
3. 设计缓存 Key，确保不同组织、用户权限和查询条件之间不会串数据。
4. 在数据更新后正确失效相关缓存，并处理缓存穿透、击穿和雪崩的基本问题。
5. 实现有边界的接口限流，并解释按 IP、用户、组织限流各自适合的场景。
6. 使用 `EXPLAIN (ANALYZE, BUFFERS)` 分析慢 SQL，结合真实查询调整索引和分页。
7. 在 Redis 不可用时让业务按预期降级，而不是整个服务不可用。
8. 用可复现的测试数据和测试步骤说明优化结果，不虚构性能提升。

### 本周完成标准

- 至少两个真实读接口接入缓存，例如知识库文档列表、工单列表或工单详情。
- 缓存 Key 包含组织标识，并包含影响结果的筛选条件和权限范围。
- 至少一个写操作会正确失效相关缓存。
- Redis 连接失败时，缓存读取退回数据库；缓存写入失败不影响主业务结果。
- 至少一个高风险接口具有限流保护，并有 429 测试。
- 至少分析并优化两个真实 SQL 查询，保留优化前后的执行计划。
- 有自动化测试覆盖缓存隔离、缓存失效、Redis 故障降级和限流。
- README 增加缓存、限流和 SQL 优化说明。

## 五、核心设计要求

### 1. 缓存什么

优先考虑：

- 知识库文档列表。
- 工单列表中的筛选结果。
- 工单详情中变化不频繁的展示字段。

谨慎考虑：

- 用户资料。
- 组织配置。
- 统计汇总。

默认不缓存：

- 当前用户是否有权限。
- 工单是否允许当前用户执行状态变更。
- 待确认的工具调用状态。
- 支付、审批或其他需要强一致性的关键状态。
- 会影响写入决策的实时数据。

**原则：缓存只能加速读取，不能代替数据库中的权限检查和业务规则判断。**

### 2. 缓存 Key

Key 必须体现数据归属和查询条件。示例仅供设计参考：

```text
nexusdesk:cache:v1:org:{org_id}:tickets:list:{query_hash}
nexusdesk:cache:v1:org:{org_id}:kb:documents:list:{query_hash}
nexusdesk:cache:v1:org:{org_id}:ticket:detail:{ticket_id}
```

要求：

- 至少包含 `org_id`。
- 如果返回结果受用户角色或可见范围影响，Key 还必须包含权限范围标识，或改为不缓存该结果。
- 列表 Key 必须覆盖状态、关键词、排序、页码/游标、页大小等影响结果的参数。
- 不要直接把未经规范化的长关键词或用户输入拼进 Key。
- 不要把密码、Token、邮箱等敏感信息写进 Key。
- 使用版本前缀，方便后续整体换 Key 格式。

### 3. TTL 与缓存失效

- TTL 不要无限期。
- 对同类 Key 加少量随机抖动，避免大量 Key 同时过期。
- 写操作成功提交数据库事务后，再执行缓存失效。
- 如果缓存失效失败，应记录日志和指标；不能回滚已经提交的业务事务。
- 先采用明确、可测试的失效策略，不要一开始引入复杂消息一致性方案。
- 对列表缓存，可以按组织维度维护版本号或使用有限范围的删除策略。选择一种并写明取舍。

特别注意：数据库事务尚未提交时，不要先删除缓存再让其他请求读到旧数据并重新写回缓存。

### 4. 缓存故障降级

缓存读取失败时：

1. 记录错误。
2. 直接执行数据库查询。
3. 不把 Redis 错误传给用户，除非业务本身确实依赖 Redis。
4. 不要无限重试 Redis。
5. 对数据库增加合理超时，防止缓存故障时流量直接压垮数据库。

缓存写入失败时，主业务读取结果仍应正常返回。缓存不是主业务成功的前提。

### 5. 缓存问题处理

- **穿透：** 对不存在的数据重复查询。可考虑短 TTL 的空值缓存，但要区分真实空结果和缓存故障。
- **击穿：** 热点 Key 过期时大量请求同时查库。可先用 singleflight 合并同进程并发请求。
- **雪崩：** 大量 Key 同时过期或 Redis 整体不可用。使用 TTL 抖动、合理超时、降级和数据库保护。

本周不要求构建复杂分布式锁。先实现并验证简单可靠的方案。

### 推荐请求流程

```text
HTTP 请求
  -> 身份认证
  -> 组织与权限范围确认
  -> 规范化查询参数
  -> 生成包含组织隔离信息的 Cache Key
  -> 查询缓存

       未命中：查询数据库 -> 写入缓存 -> 返回数据

```

- 组织 A 的缓存不能被组织 B 命中。
- Redis 停止时读接口仍可通过数据库返回结果。
- Redis 恢复后缓存功能恢复。
- 缓存写入失败不影响数据库事务结果。
- 缓存失效失败有日志，且不会伪装成失效成功。

## 十、Day 5：接口限流

### 1. 选择限流对象

建议优先保护资源消耗较高或容易被滥用的接口，例如：

- 登录接口。
- AI 对话创建或消息发送接口。
- 知识库检索接口。
- 文件上传接口。

本周至少完成一个接口。AI 消息接口可以按用户或组织限流，登录接口可以按 IP 限流。实际策略应结合现有认证流程。

### 2. 限流维度

| 维度 | 适用场景 | 注意事项 |
|---|---|---|
| IP | 登录、匿名请求 | 代理环境要正确处理可信代理头 |
| 用户 | 已登录用户的 API | 未认证请求不能伪造用户 ID |
| 组织 | 防止单个租户占用过多资源 | 需要明确组织额度和默认值 |

### 3. 算法选择

本周选择一种简单算法实现即可，例如固定窗口或令牌桶。

- 固定窗口容易理解，但窗口边界可能出现短时突发。
- 令牌桶允许一定突发流量，适合平滑控制请求速率。
- 若用 Redis 计数，必须考虑原子性。多个 Redis 命令分开执行可能产生竞态。
- 可使用 Lua 脚本把检查和计数放在一次原子操作中，但要理解脚本输入、返回值和过期设置。

### 4. HTTP 行为

- 超过限额返回 HTTP 429。
- 可设置 `Retry-After`。
- 返回统一错误结构。
- 不要在错误响应中泄露 Redis 地址、Key 或内部异常。
- 限流中间件要支持配置，不要把额度散落在业务代码里。

### 5. 故障策略

明确 Redis 限流存储不可用时的行为。对于登录和高成本 AI 接口，不应未经评估就完全放行。可以选择本地保守限流或拒绝高成本请求，并在文档中写清楚取舍。本周至少实现并测试一种明确策略。

## 十一、Day 6：SQL 分析与索引优化

### 1. 选择真实查询

从工单列表、工单详情、知识库文档列表、消息历史中选择至少两个真实 SQL。不要只优化人为编造的查询。

### 2. 记录执行计划

在测试数据库和有代表性的数据量下运行：

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT ...
```

注意：`ANALYZE` 会实际执行查询。对写 SQL 使用前先评估影响，避免在生产环境直接执行。

### 3. 分析重点

- 是否出现全表扫描。
- 实际行数与估算行数是否差距很大。
- 是否有不必要的排序。
- 是否有大量回表或随机读。
- JOIN 顺序和过滤条件是否合理。
- 是否存在 N+1 查询。
- 是否因为函数或类型转换导致索引无法使用。
- 分页是否有稳定排序条件。

### 4. 索引设计

索引要根据真实查询设计：

- 组合索引注意列顺序。
- 常用等值过滤列通常优先考虑，再结合范围过滤和排序需求。
- 不要给低选择性字段盲目建单列索引。
- 关注索引带来的写入成本和存储成本。
- 使用 migration 管理索引变更。
- 对已有重复或无用索引先收集证据，不要随意删除。

### 5. 分页

如果列表使用 `LIMIT/OFFSET`：

- 确保排序字段唯一或增加唯一字段作为第二排序条件。
- 大 offset 可能导致数据库扫描并丢弃大量行。
- 可以记录游标分页方案，但只有在本周时间充足且接口确实需要时再实施。

### 6. 优化记录

在 `query-analysis.md` 中记录：

- 原 SQL。
- 数据量和数据分布。
- 原执行计划。
- 瓶颈判断。
- 修改内容。
- 新执行计划。
- 结果差异。
- 是否增加写入成本。
- 是否通过回归测试。

不能只凭执行时间的一次变化就认定优化成功。尽量多次运行并记录中位数，同时保证测试环境、数据量和参数一致。

## 十五、常见问题排查

### 1. 明明更新了数据，接口仍返回旧内容

检查：
- 写操作是否在数据库事务提交后才失效缓存。
- 是否漏删了列表缓存或详情缓存。
- 是否存在多个版本的 Key。
- 是否有请求在失效后又把旧数据写回缓存。

### 2. 不同组织返回了相同缓存结果

立即停用相关缓存。检查 Key 是否包含组织 ID，查询是否真正加了组织条件，以及权限范围是否影响结果。不能只靠 Key 修复数据库查询本身缺少组织过滤的问题。

### 3. Redis 停止后接口大量超时

检查：
- Redis 操作是否有超时。
- 是否在错误时无限重试。
- 降级后数据库是否承受不了流量。
- 是否需要限制并发回源。
- 日志是否记录了 fallback 次数。

### 4. 限流偶尔放过超额请求

检查计数和判断是否原子执行。多个命令分开执行可能产生竞态。确认 Lua 或其他原子方案的过期时间设置正确。

### 5. 加了索引但查询更慢

检查数据量是否足以体现差异、优化器是否选择了新索引、索引是否增加了额外扫描或排序成本。不要强制使用索引来证明索引有效。

### 6. EXPLAIN ANALYZE 每次时间差异很大

检查缓存冷热状态、并发负载、数据量、参数分布和磁盘状态。统一测试条件，多次运行，记录中位数，不要只挑最好的一次。
