## 第十一周有什么实际改善

错误响应头、JSON和日志现在可以通过同一个请求ID关联。诊断入口与业务端口分离且默认关闭；启用后可以查看请求量、延迟分布、SQL调用、池等待、缓存结果、堆/GC和Worker返回情况。SQL指标只记录固定操作类别，不保存SQL文本或参数。runtime trace记录进程内HTTP、SQL和Worker活动，尚未接入跨进程分布式追踪。

真实profile显示缓存列表包的两次JSON解码是热点。改用有类型的缓存包并保证每次重复字段从空列表解码后，去掉了RawMessage的大块复制。最终5组微基准中位耗时降低约11.4%，每次分配字节降低约42.5%；最终48组业务场景共277484请求、0失败；列表平均吞吐变化约+0.95%～+5.63%，CPU缓存读取占比基本相近，不能宣称显著整体提速。原始数据、未改善的指标和可重建旧版本的源码证据见[性能报告](performance-report.md)。不能用这些短时同机数字承诺生产容量。

四类实际故障演练证明：Redis断开时列表可回源、AI不绕过限流；PG断开时存活检查正常但业务安全失败；Worker可优雅关闭，也可在运行中被终止后等待真实租约过期重新执行并只发布当前有效索引。详情见[故障报告](failure-drills.md)，这不等于已验证跨机高可用。

## 如何查看与维护

在原项目目录按[运行指南](demo/week11-demo.md)启动。前端仍访问 `http://127.0.0.1:5173`，API在8080；API/Worker分别可用6060/6061的 `/metrics` 查看诊断。已有服务运行时无需再次启动。

修改业务逻辑后运行 `python3 scripts/week11-checks.py` 和 `python3 scripts/week11-smoke.py --backend-only`；涉及交互再运行 `--web-only`。出现报错先记录 `X-Request-ID`，对照日志，再判断是数据库、Redis、Worker还是模型服务问题。不要以删除缓存、改任务状态或重新建库作为默认修复方式。

理解调用链可按 `cmd/api/main.go → config/database/observe → router → Handler → Service → Repository` 阅读；后台按 `cmd/worker/main.go → dispatcher/queue → jobs.Execute → knowledge/RAG` 阅读。先复习[可观测性说明](observability.md)和[本周问题回答](weekly/week11-answers.md)，再结合真实profile定位代码。

当前仍缺少PDF正文提取、完整成员管理/工单编辑指派删除UI、AI历史全量分页与归档、自动续流、公网部署、集中指标存储/告警和跨机追踪。第十二周可按总计划整理项目演示、简历与面试材料；代码由AI协助完成，个人独立理解和操作能力仍需通过复习与实践建立。
