# W07 builder / architecture review

Reviewed 2026-11-11 against `docs/superpowers/specs/2026-11-11-week07-design.md` (read first), repository `AGENTS.md`, W05 knowledge service/repository, W06 RAG service/index repository, migrations 00003/00007/00008/00010, configuration loading, and W08 Day 0 prerequisites. This is static design review; no runtime, tests, environment files, private objects, or backups were accessed. No production files were changed.

**Verdict: the single durable jobs table plus Asynq delivery is appropriate, but resolve the following implementation-contract blockers before treating the design as approved.** These are local choices within delegated W07 scope; they do not require user clarification or a broader framework.

## Required corrections

1. **Separate normal publication authorization from ended-attempt reconciliation.** `taskguard.Check` requires a live RUNNING lease and active actor. It necessarily rejects expired attempts, cancellation, revoked actors, and deleted parents. Recovery/cancel/final failure cleanup must therefore have its own short transaction: lock parent (including a soft-deleted parent internally), lock job, verify run/status/ended token, reset only domain rows still PROCESSING/INDEXING with that token, and transition the job atomically. Never try to invoke ordinary guarded domain `Fail` after first clearing the job lease or marking it terminal. Preserve READY rows. Ordinary worker cleanup should continue to require the live guard; rejected stale cleanup is safe because the reconciler owns recovery.

2. **Specify lock-safe scan mechanics.** A dispatcher implementation that first selects jobs `FOR UPDATE SKIP LOCKED` and then locks their documents violates parent→job ordering and can deadlock with Finish/Cancel. Select bounded candidate IDs without row locks, then process each candidate in a separate parent→job transaction with rechecked due/status predicates. Job-only dispatch reservation/heartbeat is also safe provided it never subsequently locks a parent. Do not hold batch job locks while visiting parents.

3. **Reconcile completed publication before enforcing exhausted attempts.** On attempt 3 a worker can commit index READY and crash before setting job SUCCEEDED. Recovery that simply sees `attempts == max_attempts` and fails the job produces a false failure despite completed work; recovery that refuses another claim leaves it stuck. Under the same parent→job transaction, inspect the current READY document/text/index fingerprint and reconcile the job to SUCCEEDED without incrementing attempts or invoking the model. Only unfinished exhausted work becomes FAILED. This also handles uncertain job-completion commit and avoids forcing an unnecessary fourth execution. Define whether revocation/deletion discovered before reconciliation takes precedence; hidden/deleted work must never be exposed via status APIs.

4. **Preserve the source-changed error across the existing service boundary.** `knowledge.Service.Process` records `SOURCE_CHANGED` on file hash mismatch but returns generic `knowledge.ErrStorage`. The proposed worker treats storage errors as transient, contradicting permanent source-changed failure. Add a narrow safe sentinel such as `knowledge.ErrSourceChanged` (or an equivalent typed safe processing error), return it on hash mismatch, and classify it permanent. Do not infer the cause from a later mutable document read or raw error text. Existing exported `ExtractionError.Code` and `rag.Error.Code` already support the other deterministic/transient classifications.

5. **Make lease renewal non-resurrecting and terminal delivery acknowledgments explicit.** Heartbeat must update only matching job/run/token/RUNNING with `lease_until > clock_timestamp()`; an expired lease must not become valid again just because recovery has not run. A zero-row renewal cancels the operation. Recovery should preserve the execution already counted at claim and use its attempt number for the 5s/30s delay; redelivery/no-op/dispatch failure do not consume execution attempts. Queue acknowledgment is safe after a known no-op or committed DB outcome; an unknown/failed DB transition must return a safe retryable delivery error and leave DB recovery authority intact.

## Required implementation details and verification targets

- **Context fencing:** W05 `failed(d, code)` currently creates `context.Background()` and receives no originating context; change the helper and all callers to preserve guard values through `context.WithoutCancel`. W06 Index's failure closure must likewise preserve values. Using WithoutCancel does not grant an expired token authority: the repository still verifies DB lease/run/token. Source reads and model work remain outside long transactions.
- **All legacy mutation paths:** W05 ClaimProcess and FailProcess currently use direct pool writes; W06 Fail directly updates the index. Convert these to bounded parent-first transactions when adding guard checks. Check before any reuse early return in RAG Claim as well as before writes. Sync completion/failure predicates require NULL ownership so they cannot affect asynchronous work. A schema-present synchronous claim must check nonterminal jobs atomically while holding the parent lock.
- **Historical schemas:** keep document/index public column lists free of task_token. Branch SQL only after bounded table detection inside the transaction; no async guard plus absent jobs table permits historical SQL, but an async guard plus absent table must fail closed. Existing latest-schema task_token queries must never run on migrations 7/8/10 regression fixtures. Migration 11 should constrain token shape and clear ownership when a phase ends. Retain original domain failure-code allowlists.
- **Lease check time:** use PostgreSQL `clock_timestamp()`, not transaction-start `now()`, for expiry checks. Recheck near final publication when the transaction may have performed many chunk inserts. State the achievable guarantee accurately: fencing rejects replaced/revoked ownership under the job lock; transaction commit itself cannot be made identical to an external wall-clock lease deadline. Do not hold the guard row lock over extraction or embedding.
- **Source identity:** job `source_sha256` is the uploaded file hash; index `source_content_sha256` is extracted text hash. Reconciliation must validate both roles and current extractor/model/dimension/chunker/index version. Do not compare these two different hashes directly. Existing domain READY metadata can prove publication without retaining ownership on completed domain rows.
- **Failure/reset order:** cleanup and terminal transition in one transaction avoid a terminal job leaving a PROCESSING/INDEXING domain row that no future expired-RUNNING scan can discover. If publication commit is uncertain, only reset still-owned in-progress rows; never downgrade READY.
- **Deletion:** public reads continue requiring visible parent. Internal recovery must be able to lock a soft-deleted parent and terminalize its job; using only the public visible-parent lookup can strand RUNNING jobs indefinitely. Existing Delete's document UPDATE already serializes on the parent; it need not synchronously undo completed phases.
- **Authorization:** retries retain requested_by and replace actor_user_id with the retrying creator/admin. Clarify creator means job requested_by, not document uploader. Worker must recheck actor at publication, not only at claim. Current organization membership lookup is an unlocked read; do not promise fully linearizable arbitrary concurrent membership revocation unless a consistent membership lock policy is explicitly added. The required blocked-model revocation scenario is covered by a post-model guard recheck.
- **Durable dispatch:** scanning PostgreSQL every 15s is sufficient to repair enqueue gaps and lost Redis state; a new task ID per dispatch_seq avoids dependence on Asynq uniqueness retention. Reservation and last_dispatch_error updates should be conditional on run_version and dispatch_seq, so a slow old enqueue response cannot overwrite newer-run state. Redelivery before next_run_at must not bypass backoff or consume attempts. Return an explicit known no-op rather than using any generic DB error as acknowledgment.
- **Configuration:** ASYNC_ENABLED=false should gate mutation/submission behavior consistently; keep existing API startup free of Redis ping. An independent worker may initially reuse the existing environment-only config loader, but document any JWT/HTTP settings it still requires rather than claiming those are unnecessary. Worker should receive the actual storage root and same scoped DB/model configuration through environment, not payload.
- **Public contract:** no missing mandatory W08 HTTP endpoint was found: Submit, list/status, retry/cancel plus independent `cmd/worker` cover Day 0. Existing exported knowledge Process and rag Index/IndexStatus suffice as service interfaces. Instantiate worker RAG service with its own 150s index limit; no need expose private index repositories or duplicate indexing logic. Existing rag availability also requires a generator, so either construct the current model adapter normally or narrowly split embedding-only readiness without altering Search/Ask behavior.
- **Submission/retry validation:** define PDF behavior explicitly (durable job then deterministic PDF_UNSUPPORTED failure is consistent with the stated pipeline). Submit of an existing FAILED/CANCELED dedup row returns that row rather than silently resetting it; only Retry resets attempts and increments run_version. Validate retry ownership before exposing source validation details.
- **Payload parsing:** strict exactly-three-field parsing must reject duplicate/unknown fields, noncanonical positive int64 numbers, and oversized input, not merely rely on ordinary json.Unmarshal into a struct. Safe fixed errors must also cover Asynq/default logger/error-handler output; the queue library must never log raw Redis connection errors.

## Focused acceptance additions

1. Attempt 3: commit READY, crash before job success, recover to SUCCEEDED without a fourth model call or attempt.
2. Expired token heartbeat cannot renew even before scanner recovery; its later Finish/Fail cannot overwrite new ownership.
3. Cancel/revoke/delete between domain claim and publication; cleanup remains atomic and no terminal job leaves its owned in-progress row stranded.
4. Concurrent scan/recovery and Finish/Cancel/Retry maintain parent→job ordering; bounded locks/timeouts do not hide repeated deadlocks.
5. Corrupted synthetic source yields permanent SOURCE_CHANGED, with no automatic retry.
6. Latest-schema sync claim conflicts with PENDING/RETRYING/RUNNING, while historical migration 8/10 regressions never reference new columns.
7. Redis enqueue success followed by loss, enqueue failure, and delayed old dispatch completion all recover from PostgreSQL without bypassing next_run_at or mutating a later run.

Approval can follow incorporation of the five required corrections into the design/implementation plan. No SSE, tools, general outbox, additional persistence table, or public repository interfaces are needed.

## Follow-up disposition — approved for implementation

Read the spec's binding `Accepted builder-review corrections` appendix and `.superpowers/sdd/2026-11-11-week07/task-1-brief.md`. All five blockers above are addressed: ended-attempt cleanup is distinct and atomic; scan ordering is explicit; attempt-3 publication reconciles without another execution; source-change errors preserve their permanent classification while retaining historical `errors.Is(ErrStorage)` compatibility; and heartbeat/acknowledgment rules prevent resurrection or false acknowledgment of unknown outcomes.

The appendix also settles precedence for revoked actors/deleted parents, conditional dispatch outcome updates, NULL ownership and historical SQL fallback, final publication checks, PDF submission behavior, terminal dedup behavior, and disabled-mode semantics. The brief supplies the concrete queue/domain interfaces and assigns the 150s worker indexing limit without widening W08 scope.

**Approved for implementation, with no remaining design blocker from this review.** This approval is architectural only: the focused acceptance cases and real PostgreSQL/Redis/runtime validation remain necessary implementation evidence. Follow-up involved document reads and this disposition only; no runtime or tests were run.
