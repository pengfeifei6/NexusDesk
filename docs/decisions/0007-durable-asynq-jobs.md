# ADR-0007：PostgreSQL 任务状态与 Asynq 投递

日期：2026-11-11。状态：按开发者整周委托实施；是 AI 补齐的工程选择。

## 问题

W06 同步请求需要等待模型，进程崩溃可能留下中间态。W08 需要独立 Worker 和可查询任务。单纯使用 goroutine 或仅依赖 Redis 不能保证数据库提交与投递之间的故障恢复，也不能阻止旧 Worker 迟到写入。

## 决定

使用一张 knowledge_jobs 保存业务状态、预算、版本、租约与持久投递意图；Asynq v0.26.0 负责 Redis 消息投递，独立 cmd/worker 执行。扫描器补偿未确认投递，不引入通用事件框架。任务领取和领域发布均有 PostgreSQL 条件和所有权约束。

重复提交由业务唯一键合并；重复投递由 run_version、状态、next_run_at 和租约过滤；领域结果由 task_token 与短事务保护。三层各自负责不同幂等边界，不能用消息 TaskID 替代数据库校验。

## 代价与限制

多一个本地服务和 Worker 进程；投递预留 15 秒后才重新具备补发资格，另受 2 秒扫描周期、队列积压和有界 I/O 影响，不是最大延迟保证；运行中取消不能撤销先前提交。Redis AOF 仍存在故障窗口，依赖 PG 扫描补偿。旧版本无所有权的中间态不能自动认领。既有同步 API 保留，必须重启旧 API 二进制后再运行新 Worker。

## 备选

仅 Asynq 记录状态实现更少，但缺少跨库补偿和领域所有权；通用 outbox/事件总线规模过大。本周只需文档解析和索引，选择专用任务表即可。
