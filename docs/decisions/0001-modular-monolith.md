# ADR-0001：采用模块化单体，按需增加独立 Worker

- 日期：2026-11-09
- 状态：沿用原始项目设计中的模块化单体方向；本记录由 AI 按开发者要求补齐，详细取舍待开发者阅读。
- 适用阶段：W1 工程初始化、W2～W4 工单业务及后续文档处理。
- 相关文档：[需求说明](../requirements.md)、[架构说明](../architecture.md)、[数据库设计](../database.md)。

## 1. 背景与约束

NexusDesk 是个人独立开发的 Go 后端求职项目。开发者需要兼顾研究生课业，并在约 12 周内逐步交付可演示业务、AI 功能和真实验证材料。

当前关键任务是建立组织权限、工单状态机、事务和并发领取。工单状态变化与事件必须原子提交，权限规则也需要在各入口保持一致。

项目尚处于文档设计阶段，没有真实负载、性能瓶颈或多个团队独立发布的证据。架构应便于本地运行、定位错误和解释实现。

## 2. 考虑的方案

| 方案 | 优点 | 成本与限制 | 本项目结论 |
| --- | --- | --- | --- |
| 简单单体，Handler 直接访问数据库 | 起步文件少，容易跑出接口 | 业务、协议与 SQL 容易混在一起，权限和事务难以复用 | 仅适合非常小的练习，不能作为工单业务长期组织方式 |
| 模块化单体，按领域划分内部职责 | 单进程便于启动与调试，可用普通函数调用和数据库事务协作 | 需要维护模块边界，各模块暂时一起部署，进程资源也会相互影响 | 采用 |
| 立即拆为认证、组织、工单等微服务 | 可形成独立部署和故障边界 | 增加通信、鉴权传播、超时、部署、日志关联及跨服务一致性成本 | 当前单人开发和已知需求不足以支持该成本 |

以上比较是结合本项目约束的设计判断，不是不同架构的实测性能结论。

## 3. 决策

采用模块化单体，先建立一个 `cmd/api` 应用，组织、认证和工单作为进程内模块，业务数据存放于 PostgreSQL。

具体约定：

1. 按领域组织代码，后续建立 `internal/auth`、`internal/organization`、`internal/ticket`。
2. Handler 适配 HTTP，Service 负责业务授权、规则与事务，Repository 执行 SQL。
3. 跨模块使用明确的 Go 方法或小接口，不访问其他模块私有存储实现，不在同一进程内部模拟微服务通信。
4. 启动入口组合依赖；平台能力集中管理配置、连接池和 HTTP 基础设施。
5. W1 只创建实际用到的文件，先完成健康检查、数据库连接和首条迁移。
6. W5 以后扩展文档和 AI 能力；W7 根据周计划增加 `cmd/worker`，让耗时文档任务独立于 HTTP 请求运行。
7. Worker 初期与 API 同仓库，可复用明确的业务能力和基础设施，独立进程不等于已经拆成拥有独立数据边界的微服务。
8. Redis、模型服务等依赖只在对应需求出现时接入，不成为普通工单操作的强制前置条件。

数据库共享不意味着所有模块可以任意读写全部表；模块的数据写入口和业务规则仍需维护。

## 4. 为什么适合当前项目

### 4.1 降低单人开发成本

开发者先维护一个 API 进程、一套启动流程和一个业务数据库，能集中练习 SQL、事务、权限和排障。代码调用可以在本地调试器内追踪，不必先建立服务发现、网关或跨服务调用链。

### 4.2 让核心事务保持清楚

工单修改和事件写入能够通过同一数据库事务完成。若立即分散到不同服务及数据库，必须额外处理部分成功、消息传递和补偿，明显扩大首个业务版本范围。

### 4.3 为后续演进保留边界

按领域划分代码，有助于理解职责和减少耦合。未来真的需要独立扩缩容时，可以以已有模块职责为分析起点；这不保证可以无成本拆分，仍需重新设计数据所有权与一致性。

## 5. 接受的代价

- API 中不同领域暂时一起部署，不能单独发布其中一个模块。
- 同进程模块共享资源，某个模块的阻塞或资源泄漏可能影响其他请求。
- 共享数据库和表关联会带来耦合，需要限制跨模块直接访问。
- 需要通过代码审查维持分层，单靠目录名称不能保证边界。
- 后续拆分可能需要迁移数据、重构事务和权限传播，不把拆分描述为简单搬文件。

应对措施先采用清楚的依赖关系、Context 和超时、相关测试与日志。文档处理在对应阶段独立运行 Worker，避免耗时任务占用 HTTP 请求；不提前引入整套分布式基础设施。

## 6. 什么时候重新评估

出现以下一种或多种可验证证据时，新增 ADR 重新比较方案：

| 触发条件 | 需要收集的证据 | 优先评估方向 |
| --- | --- | --- |
| 文档处理负载明显高于 API | 任务积压、资源占用、处理耗时 | 独立 Worker 的扩容与限流 |
| 某模块拖累工单响应 | profile、延迟指标、故障复现 | 查询或资源优化，必要时独立进程隔离 |
| 不同模块需要不同发布节奏 | 实际发布阻塞与回滚记录 | 独立部署是否值得承担额外成本 |
| 多个团队形成稳定所有权 | 团队职责、接口契约和运维能力 | 服务与数据边界拆分 |

没有这些证据时，优先维护现有结构。单次慢请求或学习新框架的兴趣，不足以直接得出必须拆分的结论。

## 7. 验证方式与当前状态

W1 验证启动、配置、健康检查、迁移与 README 复现；W2～W4 验证跨组织授权、状态事件事务、并发领取和业务演示。相应测试清单见架构与数据库文档。

当前只完成 ADR 文档编写，没有创建业务模块、启动服务、执行迁移或产生性能数据。开发者后续重点阅读第 2、3、5、6 节，理解选择的理由、付出的代价和重评条件。

后续架构发生变化时，新增决策记录并关联本 ADR，保留原始决策背景。
