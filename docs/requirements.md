## 1. 产品定位与目标用户

NexusDesk 面向企业内部的软件支持团队，将员工的问题提交、支持人员的处理过程和最终处理结果集中记录。首个版本提供组织隔离下的工单协作；后续加入知识库与带来源引用的 AI 问答。

首个演示场景采用虚构的软件研发企业：业务人员使用内部报表系统时遇到问题，通过 NexusDesk 提交工单；软件支持团队负责领取、沟通和解决；组织管理员维护成员角色并查看本组织处理情况。

采用这个场景的原因：问题提交者、处理者和管理员职责清楚，能够自然体现权限、状态流转、事务和并发领取，适合个人开发与 Go 后端求职展示。演示使用虚构账号和问题数据。

### 1.1 本周双角色与后续三角色规划

| 角色 | 示例 | 主要目标 |
| --- | --- | --- |
| 普通用户 `member` | 使用报表系统的业务人员 | 提交问题、补充信息、查看自己工单的进展与结果 |
| 支持人员 `support` | 软件支持工程师 | 查看本组织待处理问题、领取工单、回复并解决问题 |
| 组织管理员 `admin` | 支持团队负责人 | 管理本组织成员角色、查看本组织工单、处理关闭与重新打开 |

原设计中的“一线支持人员”和“技术处理人员”在 P0 合并为支持人员，暂不增加分组、升级处理和多级审批。

本周只落地普通成员与管理员；表中的 support 留到后续工单阶段评审。新增该角色时需要增量迁移扩展 CHECK，并同步授权与测试，不能改写已执行的成员表迁移。

### 1.2 组织的含义

组织是数据与角色的隔离边界。例如，演示组织 A 和组织 B 的成员不能互相查看工单、评论或处理事件。管理员也只能管理自己所属的组织。

用户账号与组织成员关系分开：一个账号可以属于多个组织，在不同组织拥有不同角色。一次请求只在一个经过成员关系校验的组织上下文中执行；P0 演示可先使用固定组织，不要求提供多组织切换页面。

## 2. 要解决的真实问题

| 当前问题 | 对使用者的影响 | P0 提供的改善 |
| --- | --- | --- |
| 问题散落在聊天记录中 | 容易漏处理，难以知道是否有人负责 | 为每个问题建立独立工单，记录负责人和状态 |
| 多人同时响应同一问题 | 重复劳动，责任归属不清 | 领取后明确处理人，并发领取只允许一人成功 |
| 处理过程缺少记录 | 反复询问进度，难以回顾原因 | 保留评论和状态变化记录 |
| 不同团队的数据混在一起 | 容易看到不属于自己的问题 | 按组织和角色限制数据访问 |
| 相似问题反复出现、知识分散 | 支持人员重复搜索和解释 | P1 接入知识库与 AI 问答，P0 先积累处理记录 |

## 3. 一条完整的核心流程

示例问题：普通用户小林无法导出月度报表。

1. 小林登录，系统确认其为组织 A 的有效成员。
2. 小林填写标题“月度报表导出失败”和问题描述，提交工单。
3. 系统创建 `OPEN` 工单，关联组织 A 和创建人，初始没有处理人。
4. 组织 A 的支持人员在待处理列表看到工单；其他普通用户看不到小林的工单。
5. 支持人员小周领取工单，成为处理人，状态变为 `IN_PROGRESS`。
6. 如果另一名支持人员同时领取，只有一个请求成功，另一个收到冲突提示。
7. 小周通过评论询问复现条件，小林补充信息；评论与工单采用相同的可见范围。
8. 小周写明解决办法并将工单变为 `RESOLVED`，状态变化和处理事件一起保存。
9. 小林确认恢复后关闭工单，状态变为 `CLOSED`；组织管理员也可以关闭已解决的工单。
10. 如果在关闭前发现问题仍未解决，管理员可以将 `RESOLVED` 工单重新打开为 `IN_PROGRESS`，保留原处理人和历史记录。

上述流程完全通过后端业务接口完成，不依赖模型服务。前端在第 4 周接入。

### 3.1 状态转换规则

| 当前状态 | 目标状态 | 允许的操作者 | 必要条件 |
| --- | --- | --- | --- |
| 无 | `OPEN` | 本组织有效成员 | 创建参数有效，组织和创建人由后端确认 |
| `OPEN` | `IN_PROGRESS` | 本组织支持人员 | 尚未领取；成功者成为处理人 |
| `IN_PROGRESS` | `RESOLVED` | 当前处理人，且仍具支持角色 | 提供非空解决说明，并记录处理事件 |
| `RESOLVED` | `CLOSED` | 创建人或本组织管理员 | 工单仍处于已解决状态 |
| `RESOLVED` | `IN_PROGRESS` | 本组织管理员 | 提供重新打开的原因，保留原处理人 |

未列出的转换统一拒绝。P0 不提供关闭后重新打开、自动关闭、任意状态覆盖或转派功能。状态变化与对应事件必须在同一个数据库事务中完成。

## 4. 权限边界

| 操作 | 普通用户 | 支持人员 | 组织管理员 |
| --- | --- | --- | --- |
| 在当前组织创建工单 | 允许 | 允许 | 允许 |
| 查看工单列表、详情和历史 | 仅自己创建的 | 本组织全部工单 | 本组织全部工单 |
| 添加评论 | 仅自己创建且未关闭的工单 | 本组织未关闭的工单 | 本组织未关闭的工单 |
| 修改标题、描述和优先级 | 仅自己创建且仍为 `OPEN` 的工单 | 同左，不因支持角色额外扩大编辑权 | 同左，不因管理角色额外扩大编辑权 |
| 领取工单 | 禁止 | 本组织未领取的 `OPEN` 工单 | 禁止；P0 管理员不兼任支持角色 |
| 标记解决 | 禁止 | 仅自己领取且处于处理中的工单 | 禁止 |
| 关闭已解决工单 | 仅自己创建的 | 仅自己创建的 | 本组织全部工单 |
| 重新打开已解决工单 | 禁止 | 禁止 | 本组织全部工单 |
| 查看组织成员（W02） | 本组织 active 成员允许 | 未来扩展，不在 W02 取值内 | 本组织 active 成员允许 |
| 添加已注册成员（W02） | 禁止 | 未来扩展，不在 W02 取值内 | 仅本组织 active admin |
| 修改成员角色（后续阶段） | 禁止 | 禁止 | 仅本组织；W02 无此接口 |

补充规则：

- 角色来自当前组织的有效成员关系，客户端提交的角色、创建人或处理人不能直接作为授权依据。
- 列表、详情、评论和事件都检查权限，不能只在前端隐藏按钮。
- 非本组织资源或对当前用户不可见的工单统一返回 `404`，避免暴露对象是否存在。
- 对已可见资源执行不允许的操作，返回 `403`；当前业务状态不满足操作条件时返回 `409`。
- P0 不提供工单、评论和处理事件的删除入口，保留处理历史。

## 5. 三个用户故事与验收标准

### US-01：普通用户提交和跟踪自己的问题

作为普通用户，我希望提交软件使用问题，并查看自己工单的进度、回复和处理结果，以便知道问题由谁负责以及是否已经解决。

| 编号 | 场景与操作 | 可测试的预期结果 |
| --- | --- | --- |
| AC-01-1 | 已登录的组织 A 成员提交有效标题和描述 | 返回 `201` 和工单 ID；记录归属 A、创建人正确、状态为 `OPEN`、处理人为空 |
| AC-01-2 | 标题或描述为空白，或者标题超过 200 个字符 | 返回 `400`，不产生工单记录 |
| AC-01-3 | 用户查询列表和详情 | 列表仅包含当前组织内自己创建的工单；可查看这些工单的评论与状态历史 |
| AC-01-4 | 用户访问同组织其他普通用户的工单，或组织 B 的工单、评论、事件 | 返回 `404`，响应不包含目标内容 |
| AC-01-5 | 未登录用户尝试创建工单 | 返回 `401`，不产生工单记录 |
| AC-01-6 | 创建人关闭自己的已解决工单 | 返回成功；状态为 `CLOSED`，有且仅有一条对应关闭事件；再次关闭返回 `409` |

### US-02：支持人员领取并处理工单

作为支持人员，我希望从本组织待处理列表领取工单，与提问者沟通并记录解决结果，以便明确责任并形成可追溯的处理过程。

| 编号 | 场景与操作 | 可测试的预期结果 |
| --- | --- | --- |
| AC-02-1 | 支持人员领取本组织未领取的 `OPEN` 工单 | 返回成功；处理人变为本人、状态为 `IN_PROGRESS`，生成一条领取事件 |
| AC-02-2 | 两名支持人员并发领取同一工单 | 恰好一个成功、另一个返回 `409`；最终只有一个处理人和一条领取事件 |
| AC-02-3 | 当前处理人提交解决说明并标记解决 | 状态变为 `RESOLVED`，说明和状态变化事件可查询 |
| AC-02-4 | 其他支持人员尝试解决不属于自己的工单，或普通用户尝试领取 | 返回 `403`，处理人、状态和事件均不改变 |
| AC-02-5 | 直接将 `OPEN` 工单标记解决，或解决说明为空白 | 分别返回 `409` 或 `400`，不留下部分更新 |
| AC-02-6 | 模拟状态更新后的事件写入失败 | 整个事务回滚，工单状态和事件记录均保持操作前状态 |

并发验收在第 4 周完成；第一周只明确需求，不提前实现领取逻辑。

### US-03：管理员维护组织角色和查看处理情况

W02 先完成组织创建、成员列表与添加已注册用户。下述角色变更、support 和工单用例保留为后续业务验收，不列为 W02 完成条件；成员列表已不再限定管理员，见第 4 节及本周 API 契约。

作为组织管理员，我希望查看本组织成员、调整角色并跟踪本组织工单，以便安排支持职责，同时保持组织之间的数据隔离。

| 编号 | 场景与操作 | 可测试的预期结果 |
| --- | --- | --- |
| AC-03-1 | 管理员查询成员和工单列表 | 仅返回当前组织数据，不包含其他组织的成员或工单 |
| AC-03-2 | 管理员把本组织某普通成员设为支持人员 | 角色更新成功；该成员后续请求可以领取本组织待处理工单，客户端不能自行获得此权限 |
| AC-03-3 | 普通用户或支持人员修改角色，或管理员操作其他组织成员 | 前者返回 `403`，后者返回 `404`；成员关系不变 |
| AC-03-4 | 管理员试图将组织最后一名管理员降级，包括并发降级 | 返回 `409`；组织始终至少保留一名管理员 |
| AC-03-5 | 管理员重新打开本组织已解决工单并填写原因 | 状态变为 `IN_PROGRESS`，保留原处理人，新增包含操作者和原因的事件 |
| AC-03-6 | 把仍有 `IN_PROGRESS` 或 `RESOLVED` 工单的处理人降为非支持角色 | 返回 `409`，避免工单失去可处理人员；P0 可先完成并关闭工单再降级 |

### 8.2 首个业务版本 G1（第 4 周）

使用两个组织、至少两名支持人员和不同角色的虚构账号验证：

1. 普通用户能登录、建单、补充评论、查看结果并关闭工单。
2. 支持人员能领取和解决问题，两人并发领取时仅一人成功。
3. 管理员能管理成员角色、查看本组织工单并重新打开已解决工单。
4. 同组织普通用户之间及不同组织之间的越权访问均被拒绝。
5. 非法状态转换和事件写入失败不会留下错误状态或半成品数据。
6. 按 README 可以复现上述流程；结果有测试或演示证据。

## 9. 本稿采用的设计取舍与原文衔接

以下是本次 AI 补齐的产品建议，不表示开发者已经逐条确认或掌握：

| 取舍 | 本稿采用的方案 | 原因与代价 |
| --- | --- | --- |
| 业务场景 | 企业内部软件支持 | 能覆盖原设计核心能力，避免客户门户、付费和客服渠道扩大范围 |
| 支持角色 | 合并一线支持与技术处理人员 | 降低个人项目权限复杂度，暂不展示多级支持流程 |
| 工单可见范围 | 普通用户仅本人，支持与管理员可见本组织全部 | 权限清楚、可测试；更细的团队隔离留待后续 |
| 管理与处理分工 | P0 单个组织成员只有一个角色，管理员不兼任处理人 | 避免隐含权限继承，演示使用独立账号 |
| 关闭与重开 | 创建人或管理员关闭；管理员在关闭前重开 | 明确状态转换责任，关闭后重开暂缓 |
| 编辑与删除 | 创建人仅在待处理时编辑；P0 暂缓删除入口 | 保留处理证据；收窄原设计“CRUD”中删除的范围 |
| 成员维护 | W02 先建立组织与添加已注册成员，角色修改后续实现 | 注册只创建账号；登录用户主动创建组织并事务内成为 admin；active 成员可读成员列表，邀请流程后续补充 |
| 操作事件 | 随第 3 周状态机实现 | 原设计优先级表将事件列在 P1，但流程和周计划要求事务内写事件，本稿采用后者 |
| 文件上传 | 按周计划在第 5 周开始 | 原设计将文件元数据与上传列在 P0，但不将其作为第 4 周 G1 的前置条件 |

本文将上述差异显式记录，未修改原始设计与开发手册。后续调整应同步修改相关验收条件。

## 10. 阅读与学习交接

本次已完成：AI 生成需求初稿，并补齐权限、状态流转、异常场景及阶段边界。
