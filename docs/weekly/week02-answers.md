## 1. Day 1：身份、组织与契约

### Q01：身份认证和授权分别解决什么问题？

认证回答“当前请求是否持有本系统接受的身份凭据”；授权回答“这个身份能否对这个组织或对象做这项操作”。两者不能互相替代。

在本项目中，RequireUser验证Token并查询账号仍存在，得到可信用户ID。MemberService再查询目标组织的active成员关系，policy根据admin/member决定动作。Bob能登录，不代表他是A组织成员；Bob在B组织是admin，也不代表能管理A。

### Q02：users、organization_members和member角色有什么区别？

users是全局账号；organization_members是某用户与某组织之间的一条关系；member是该关系允许的角色值之一，另一个值是admin。

成员关系必须关联已有用户，但用户可以暂时没有组织。同一用户在不同组织可有不同角色。不能把用户行中的全局角色或某组织的admin身份用于其他组织；当前没有独立member_id，关系由(org_id,user_id)标识。

### Q03：为什么前端传来的user_id、org_id、role不能直接当权限依据？

客户端能修改URL、JSON和请求头，隐藏按钮不能阻止直接发HTTP请求。orgID只是想访问的目标，必须验证当前用户在该组织的关系；操作者ID来自验签后的上下文。

组织创建只接name，后端设置创建者admin/active。添加成员的user_id是合法的“目标用户”，不是操作者；额外owner_id、actor_id、org_id或status不能替换身份。具体例子见Q31。

### Q04：为什么注册不自动创建组织？

注册建立账号身份，创建组织建立租户及首名管理员。分开后，一个账号可以先无组织，之后创建或加入多个组织；不会把账号永久绑定到单一租户。

当前注册成功201只返回id/email/display_name，不返回Token或创建组织。登录成功后再调用创建组织接口；首条admin/active关系与组织同事务写入。

### Q05：本周七个API与范围边界是什么？

| API | 身份条件与用途 |
| --- | --- |
| POST /auth/register | 公开，创建账号 |
| POST /auth/login | 公开，验证密码后签发凭据 |
| GET /me | 当前有效用户，返回本人公开资料 |
| POST /organizations | 当前有效用户，创建组织与首名admin |
| GET /organizations | 当前有效用户，只看本人active组织 |
| GET /organizations/:orgID/members | 目标组织active member/admin |
| POST /organizations/:orgID/members | 目标组织active admin，添加现有用户 |

表内统一前缀/api/v1，原GET /healthz保持公开。角色只允许admin/member，状态active/disabled；没有support、邀请、角色修改、停用、刷新Token、工单或前端接口。完整输入/错误见 [API契约](../api/auth-organization.md)。

## 2. Day 2：数据库约束、迁移与存储职责

### Q06：为什么邮箱唯一性必须由数据库保证，不能只靠SELECT？

两个请求可能同时查到“邮箱不存在”，随后都插入。应用预查不能关闭这个并发窗口；数据库唯一索引才是最终防线。

本项目先去首尾空白并小写化邮箱，再用users_email_ci_unique对lower(email)建立唯一索引。并发重复时一个成功，另一个被数据库拒绝；只把SQLSTATE 23505且对应这个索引的错误映射为409，不把所有数据库异常当重复。相关实现见 [用户Repository](../../internal/auth/repository.go)。

### Q07：联合主键、外键、CHECK各解决什么？它们能替代授权吗？

联合主键防止同用户在同组织有两条关系；外键保证关联账号和组织存在；CHECK限制role/status允许值。

这些约束不会证明当前请求者是谁，也不会验证他是否是admin。知道合法orgID、user_id甚至有外键，都不等于有操作权限。授权由可信身份和当前成员查询完成，数据库约束负责另一层数据一致性。

### Q08：为什么用00002/00003增量迁移，为什么不重写00001？

已经执行的迁移是历史，改写它会让不同数据库中的实际结构与版本记录不一致。本周保留00001组织表，00002建用户及邮箱索引，00003建成员及约束。

成员表依赖用户和组织，升级按顺序执行，回滚按反序。测试脚本只在自己的可丢弃库验证1→3→1→3；日常库遇到失败先查Goose状态和错误，不能把自动Down或删卷当修复方法。

### Q09：Handler、Service、Repository分别负责什么？为什么设置Context和超时？

Handler处理HTTP、严格参数与响应DTO；Service处理策略、授权和原子业务动作；Repository执行参数化SQL、转换记录和分类数据库错误。

普通SQL最多3秒，创建组织/添加成员事务最多5秒；更早的父Context截止时间优先。rows要关闭并检查遍历错误。取消与故障应向上传播，不能变成“查无记录”或成功。事务由专用Repository方法持有同一个tx，Service不再嵌套开第二个事务。

## 3. Day 3：注册、密码与严格输入

### Q10：Argon2id与直接SHA-256存密码有什么区别？

SHA-256计算很快，适合完整性等场景，但泄露密码摘要后，攻击者也能高速猜测。Argon2id针对密码存储设计，可以用内存、迭代和并行参数提高每次离线猜测成本。

本项目用alexedwards/argon2id封装，不自创算法。较慢不代表无法破解，也不代替弱密码检查、限流和凭据保护。原理参考 [OWASP密码存储说明](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)，本项目具体参数见Q14。

### Q11：随机盐有什么作用？盐需要保密吗？

每次Hash使用新的安全随机盐，使相同密码也得到不同存储编码，减少跨用户复用预计算猜测结果的价值。盐可与参数和散列一起存储，不是必须保密的签名密钥。

本周盐16字节，测试同一密码两次编码不同且都能正确验证。不要把“随机盐”理解成每次登录随意生成新盐后比字符串：验证使用存储编码中的原盐和参数。

### Q12：登录是在解密密码吗？怎样验证？

不是解密。注册保存含算法、版本、参数、盐、派生值的编码；登录把输入原文与该编码交给VerifyPassword验证，不需要取回原密码。

实现先限制编码长度、支持的参数和成本，再调用库的验证能力，避免异常存储值触发巨大资源分配。不要自行解析出散列后用普通字符串比较，也不要将两个不同盐的新Hash结果直接比较。库接口见 [argon2id文档](https://github.com/alexedwards/argon2id)，包装见 [password.go](../../internal/auth/password.go)。

### Q13：密码为何保留空格和NUL，而显示名、组织名不能包含NUL？

密码有效UTF-8、15～128码点且最多512字节，非全空白；不裁剪、不截断、不做Unicode规范化。去掉原密码中的空格或NUL会改变用户输入，可能造成错误匹配或无法登录。

显示名/组织名作为PostgreSQL文本持久化，U+0000不被该存储类型接受，应在Service中返回400。密码中的NUL只参与内存散列，数据库保存的编码不含该原始字符，两者边界不同。

### Q14：实际Argon2id成本和两个并发名额意味着什么？503是不是登录限流？

当前参数为19456KiB内存、2次迭代、并行度1、盐16字节、派生值32字节；注册和登录共用一个PasswordHasher，最多两个计算同时运行，超额503 AUTH_BUSY。

这是进程资源预算，不是按账号/IP统计的防暴力破解限流，也不是429。已开始的库计算不能靠Context立即中断，完成后释放名额；若请求已取消，不继续写库。本机小样本成本及限制见 [Day3基准](evidence/week02-day3-password-benchmark.json)，不能据此宣称生产吞吐或P95。

### Q15：邮箱和显示名为什么规范化，密码却不规范化？

邮箱作为本项目的ASCII登录标识去首尾空白并统一小写，保持注册和查找一致；不会擅自删除点号或+tag。显示名/组织名去首尾空白以符合展示规则。

密码的原文就是验证依据，改变原文会影响认证。输入字节长度、码点长度和允许字符应明确区分，不能用数据库文本字段的限制替代密码策略。

### Q16：为什么不直接依赖Gin默认JSON绑定？

本项目需要严格字段名、拒绝未知/重复字段、只允许单个对象、无尾随值、合法UTF-8与成对Unicode转义。标准解码器可能替换无效代理项，或者默认接受重复字段的后值，不能满足全部契约。

本周在有界读取和Unicode检查后，使用token方式检查对象字段，数值保留RawMessage再验证。成员user_id必须是正int64 JSON整数，99.0、9e1、字符串、null或溢出均400；不能先转float64再强转整数。注册/登录继续复用同一严格入口。

### Q17：怎样证明没有泄露密码散列和Token？

响应使用显式公开DTO，敏感模型字段带JSON隐藏标签；用户/成员响应字段都有断言。登录成功响应允许返回access_token，这是凭据交付，不允许顺带返回密码或散列。

应用不使用记录全部请求头/响应体的日志器；真实进程测试检查输出不含测试密码、散列、密钥和本次Token，归档仅保存安全摘要。有限测试不能证明所有未来日志路径永远安全，新增观测功能必须重新审查。

## 4. Day 4：登录与JWT

### Q18：为什么不存在邮箱与错误密码返回相同401？dummy hash有什么用？

不同错误容易帮助探测账号是否存在。不查到邮箱就立即退出也可能产生明显耗时差异，所以服务启动时生成一次同参数dummy hash，未知邮箱也验证一次密码。

未知邮箱无论dummy是否匹配都不能登录，必须同时有真实用户和正确密码。dummy减少明显差异，不保证网络恒定时间；损坏散列、资源忙、数据库故障仍分别按内部故障或503处理，不能一概伪装成401。注册409仍会暴露邮箱重复，这是已记录的本地演示取舍。

### Q19：JWT三段是什么？Payload为什么不能放密码或敏感信息？

三段为Base64URL编码的Header、Payload、Signature。Header声明算法，Payload保存Claim，签名保护前两段的完整性。

编码不是加密，持有Token就能解出Payload；签名也不会隐藏内容。本项目只签发sub/iss/aud/iat/exp，不放密码、散列、密钥、角色或组织资料。能解码只表示看到了数据，必须验签及校验内容后才能信任身份；详见 [JWT说明](../jwt-guide.md)。

### Q20：算法白名单、签名、issuer、audience、exp分别解决什么？

| 检查 | 回答的问题 |
| --- | --- |
| 算法白名单HS256 | 这个凭据是否采用服务端明确接受的算法 |
| 签名 | 内容是否由持有正确密钥的一方签出、是否被改动 |
| iss | 是否来自配置的发行方 |
| aud | 是否面向本API接受的受众 |
| exp | 当前时刻是否仍在有效期内 |

它们不能互相替代：签名正确的其他系统Token，也可能不该被本API接受。必需字段的存在性不能依赖宽松默认值；本项目显式配置库选项并补检查，拒绝none、HS384、错误密钥/发行方/受众。参考 [golang-jwt验证选项](https://golang-jwt.github.io/jwt/usage/parse/)。

### Q21：sub、iat、nbf、整数时间和长度预算还有什么要求？

sub为规范正十进制int64用户ID字符串，拒绝0、负数、前导零和溢出。iat必需且不晚于当前；exp必需、尚未到期且大于iat，寿命最多900秒；nbf不主动签发，出现时校验已生效。本周无时钟宽限。

时间仅接受int64十进制JSON整数秒，拒绝小数、指数、字符串、null；避免库默认秒精度截断放宽边界。Token最多8KiB，issuer/audience各最多256字节；预算考虑JSON转义膨胀，签发后也检查长度。相关真实Bug见Q37。

### Q22：JWT_SECRET_BASE64应该如何配置？为什么不能直接用Base64文本签名？

配置约定密钥是标准Base64规范编码，解码后至少32字节；双方必须用相同的解码字节，不能一边用字节、另一边拿编码文本做HMAC。TokenManager还复制密钥切片，防止外部修改影响行为。

Day4起共12个必需变量，新增JWT_ISSUER、JWT_AUDIENCE、JWT_TTL_MINUTES=15、JWT_SECRET_BASE64。已有.env不会被模板自动补齐，由开发者本机维护；示例密钥占位不能当有效配置。本次测试只用临时虚构值，不要求把真实密钥交给AI。

### Q23：15分钟到期后怎么办？删除客户端Token等于注销吗？

当前没有Refresh Token和服务端撤销表，到期重新登录。客户端删除自己的副本，不会让已复制出去的Token立即失效；轮换单一签名密钥也不是精细的单用户会话撤销方案。

账号已删除时中间件每次查询会拒绝；某组织disabled时成员授权拒绝该组织。这两条规则也不等于完善的会话管理。Day7演示使用测试密钥在内存构造已过期凭据，不修改生产时钟，也不把Token保存到文件。

## 5. Day 5：可信上下文、组织事务与本人列表

### Q24：Gin中间件怎样向Handler传递可信用户ID？

RequireUser只接受唯一Authorization，Bearer与Token间固定一个ASCII空格，scheme大小写不敏感。验证签名/Claim后再查询用户存在，成功才将int64用户ID写入私有上下文键。

Handler通过CurrentUserID取值并检查类型/正数，不从JSON取操作者。上下文只存ID，不存Token、密码或密钥；/me再取公开用户字段。健康检查、注册、登录不挂保护组，其他五个接口都要经过认证。

### Q25：为什么JWT有效还不能读组织A？

有效Token只说明账号凭据可被接受，还必须确认账号存在、请求orgID合法、该用户在A组织有active关系，之后才按动作判断角色。

因此JWT无效401；已认证但非成员/disabled/组织不存在统一404；active member尝试添加403。统一404减少组织存在性泄露，不能把内部数据库异常也吞成404。

### Q26：创建组织和首名admin为什么放一个事务？

业务承诺是“创建可由当前用户管理的组织”。若只成功写组织、管理员关系失败，会留下孤立组织。两步使用同一个tx，提交成功才共同生效，失败整体回滚。

本项目真实测试故意使第二步失败，还使延迟约束在COMMIT失败，均没有留下组织。原理见 [PostgreSQL事务说明](https://www.postgresql.org/docs/17/tutorial-transactions.html)，本项目实现见 [事务指南](../organization-transaction-guide.md)。

### Q27：为什么不能混用pool.Exec与tx.Exec？为什么回滚用独立Context？

pool可能选另一条连接，脱离本事务；同一业务原子动作必须共用tx。两次SQL完成不等于提交完成，COMMIT出错不能返回201。

父Context取消后直接复用它清理可能立即失败，所以回滚用独立最多3秒Context。回滚不保证Identity编号连续；提交时网络中断可能造成结果不确定，没有幂等键时不能自动重试整个创建请求并声称恰好一次。

### Q28：本人组织列表为什么先过滤再分页？

先按可信user_id和active成员关系过滤，再按组织ID排序和LIMIT/OFFSET；否则他人或disabled记录会占据页槽，出现错误空页或越权结果。

page/page_size默认1/20，单页最大100，拒绝重复/未知/非数字/偏移溢出，空结果为[]，my_role读取数据库当前关系。合法但很远的页可以为空，不应为了返回空页而放宽整数溢出校验。

## 6. Day 6：组织RBAC与负向测试

### Q29：用户在组织被禁用，但旧JWT未到期，怎样拒绝？

不把组织角色或状态当作Token中的固定授权。每个组织请求重新查询当前关系，disabled不能通过active过滤，读写该组织统一404；原JWT在其他有效组织仍可用，/me也不因单个组织禁用而失效。

真实测试先签发Token再UPDATE测试关系，原Token被拒绝。注意这保证后续请求按当前查询授权，不自动保证与已经在途的写入完全线性化，边界见Q34。

### Q30：为什么Handler授权后Service还授权一次？

Handler先授权，确保非成员或member不能借非法JSON/目标是否存在探测信息；Service入口再授权，确保其他调用方绕过Handler直接调用也不能跳过权限。

代价是合法HTTP有两次成员查询。本周选择小范围显式接口，不设计通用权限缓存；如果将来优化，必须同时保住HTTP错误顺序和Service自身授权，不能简单删除其中一层。

### Q31：添加请求里允许user_id，为什么不算信任前端身份？

这是要加入的目标用户，不是发起请求的操作者。例如Alice的Token在A为admin，请求user_id=Bob会为Bob建立关系，但操作者始终是Alice。

Bob在A为member，即使传role=admin，也只是要求添加目标为admin，不能把自己当前权限升级；授权先判断Bob仍是member，返回403。extra actor_id/owner_id/org_id/status也不能替换可信上下文或URL组织。

### Q32：为什么重复disabled也409？并发怎么保证只有一条？

添加接口只建立新关系，不是恢复或修改接口。已有disabled关系仍占用联合主键，返回409并保留原角色/状态；用UPSERT会偷偷扩展为状态/角色变更，违反契约。

两名admin并发添加同一目标，依靠主键使一个201、另一个409。不能用“先查不存在”代替这个约束，也不能把任何23505都误映射为成员重复。

### Q33：成员查询有哪些防泄露规则？

FindActiveMembership同时限定org_id、当前user_id、active；ListMembers只查已经授权的org_id，关联users时只取显示名，不做全局成员查询后再让前端过滤。

列表包含该组织active/disabled关系，按user_id升序分页，仅返回五个公开字段。没有邮箱、密码散列和独立member_id；错误响应也不带原始SQL/DSN。目标不存在的USER_NOT_FOUND只允许已授权admin看到。

### Q34：每请求查权限是否彻底解决了并发撤权？

没有。请求查到admin后，另一事务可能立即撤权，而原请求已开始后续写入。本周没有撤权API，也没有承诺授权检查与写入完全线性化。

以后若有强一致撤权需求，需要定义提交语义、锁定范围或条件写入等方案，再补并发测试。当前“旧Token不能绕过已禁用关系”的测试，不能被夸大成解决所有撤权竞争。

## 7. Day 7：验证、审查、复盘与交接

### Q35：普通测试Skip代表什么？race能证明数据库权限正确吗？

普通测试不启用真实数据库，六个入口明确Skip。只有隔离运行器启用对应开关、库名前缀和回环地址检查后才实际执行，Skip不能算Pass。

race检查Go共享内存数据竞争，不替代数据库唯一约束、事务回滚或跨组织负向测试；vet检查部分可疑模式，build检查编译，go mod verify核对缓存模块完整性，都不能证明系统没有漏洞。本地通过也不等于远程CI已运行，最新数量见 [统计摘要](evidence/week02-day7-test-summary.json)。

### Q36：怎样证明本周目标流程可复现？

从明确源码清单创建不含.env/.git/生成缓存的新目录，按独立运行器启动专用库、迁移和真实API进程，按Alice/Bob顺序请求并核对数据库，再用过期凭据验证401。

本次使用/var/tmp快照、现有主机工具、Go缓存和本地postgres:17；它证明干净项目目录流程，不等于全新机器已安装依赖或真实配置已填好。执行者是AI，未录视频，不冒充开发者亲自演示。结果见 [演示记录](week02-demo.md)。

### Q38：AI完成工程任务，和本人独立掌握有什么区别？

工程交付可以由源码、自动化测试、实际演示和审查证明；个人掌握需要自己解释设计、定位边界并复现关键路径。两种证据不能互换。

本周设计/代码/验证按委托由AI完成。可先自己口述十题，再回看对应Q与源码；答不出就定位测试、修改一个临时夹具观察结果，再总结原因。本文不代填个人分数、独立实现清单或已掌握结论。

### Q39：第三周工单怎样接上当前身份与组织？

沿用RequireUser提供的可信user_id，工单表必须带org_id；每次请求先验证当前组织关系，再检查目标工单属于该组织和对象级权限。拥有组织成员资格不自动等于能修改所有工单。

tickets记录当前状态，ticket_comments记录讨论，ticket_events记录业务变化。工单修改和相应事件必须同事务；子记录要防止把另一组织的ticket_id关联进来，可按既有设计评估(org_id,ticket_id)复合约束。新表、状态机和support规则需按第三周手册落实，不改写本周迁移或提前宣称已实现。

### Q40：为什么Day7没有自动提交Git？怎样保存本周成果？

AGENTS要求另行明确授权才commit/push；原始手册建议的命令是参考材料，不自动构成本次提交授权。本次保留开发者已有HEAD和未提交成果，用源码清单标识交付，不伪装新版本。

先检查git status、git diff、未跟踪文件和.gitignore，再按功能暂存必要路径，检查git diff --cached后自行提交。真实.env、密钥和Token不能进入仓库；不要只检查已跟踪Diff而漏掉新文件，也不能把临时凭据拷到文档方便复习。

### Q41：遇到本周问题，怎样排查而不扩大影响？

先记录预期/实际状态和数据库副作用，使用虚构输入在隔离环境复现，缩小到Handler、Service、Repository或配置边界；提出可验证假设，补最小失败测试，修复后运行相关和全量回归。

不要先关闭鉴权、降低散列参数、吞错误或删断言让测试变绿。迁移/卷/数据相关问题先只读检查，不在日常库自动回滚、删卷；凭据问题用本地断言和安全摘要，不打印秘密交给AI。

## 8. 手册常见故障：现象、原因与排查回答

以下是可能遇到的故障，不表示本周每项都真实发生过。

| 现象 | 先检查的原因 | 最小验证与处理 |
| --- | --- | --- |
| 重复注册仍201 | 未迁移到3、错误数据库、缺lower(email)唯一索引、未识别指定冲突 | 在隔离库并发注册大小写邮箱，确认一201一409；核对索引与库名，不靠SELECT预查 |
| 登录总是401 | 密码原文被裁剪、查错账号/库、把新盐Hash字符串直接比较 | 用测试用户走注册→登录，保留原文验证存储编码；不输出密码/编码 |
| 登录返回500 | 存储散列损坏、参数不支持、查询或签发故障 | 区分Service静态错误和DB可达性；用受控夹具复现，不能全改401掩盖故障 |
| JWT始终无效 | 编码文本/解码字节混用、密钥/iss/aud不同、算法/时钟/sub不符 | 在本地用TokenManager自签发/自验证，核对非秘密配置及必需Claim，不粘贴真实Token |
| 到期仍能访问 | 路由没挂中间件、仅解码没验证、时间校验缺失 | 运行受保护HTTP与--closeout过期401；健康/登录本来公开，不能拿它们验证过期行为 |
| API启动缺JWT变量 | 老.env只有W1八项；Go不自动加载.env | 按README本机补四项并加载；示例保留占位，错误只看字段名，不打印整个配置 |
| 合法Token仍401 | 重复Authorization、空白格式、账号删除、凭据过期 | 使用单头单空格Bearer；先测/me，再组织接口，分开身份与成员问题 |
| 可读他人组织 | SQL少org_id/user_id条件、复用其他组织角色、漏Service授权 | 用两个账号/两个组织交换URL，要求统一404并查无写入，追查参数化WHERE |
| 组织只写一张表 | 第二次SQL用pool、漏回滚、忽略COMMIT错误 | 同tx写入；隔离库故意第二步/提交失败，检查组织0条而非只看HTTP |
| 401/403/404混乱 | 把未认证、非成员、角色不足和DB故障混为一谈 | 依次验证身份→路径→active关系→角色；缺身份401、非成员404、member写403、故障500 |
| 添加disabled后被恢复 | 使用UPSERT或先更新状态 | 仅INSERT，已有关系409；核对原role/status保持不变 |
| member能探测目标用户 | 查询目标/解析业务对象早于权限判断 | 存在/不存在目标和非法JSON都先403；非成员都先404 |
| 分页漏项/泄露 | 先分页后过滤、排序不稳定、偏移溢出 | 先过滤active本人关系或限定org_id，再排序分页；测试disabled占位与巨大页码 |
| 503 AUTH_BUSY | 同进程两个密码计算名额已用完 | 控制并发并测名额释放/取消；不把它当已完成账号限流，也不每请求new Hasher |
| 迁移失败 | 外键依赖顺序、版本/索引冲突、连接到别库 | 只读核对Goose status和目标库；修正原因后在专用库实验，不自动回滚日常数据 |
| 集成测试污染数据 | 手工开启开关指向开发库、继承环境或清理范围过大 | 使用--closeout运行器、回环+专用前缀、随机项目；只清理本次有归属的资源 |
| race通过却有并发重复 | 把内存竞争检查当数据库约束测试 | 真实并发两admin添加，检查状态一201一409和数据库仅一条 |
| 普通Go全绿却未验证DB | 六个入口Skip被计为Pass | 分别读普通/隔离库统计；使用明确运行器并保存实际退出码 |
