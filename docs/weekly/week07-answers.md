# 第七周开发问题参考回答

对应[第七周手册](../../项目开发文件/每周开发手册/10_NexusDesk_第七周详细开发手册.md)的20道复习题。以下由AI根据实际实现整理，是阅读材料，不代表开发者已经独立掌握。

## 1. 为什么HTTP请求内启动goroutine不等于可靠异步任务？

goroutine 只存在于当前进程内。请求结束后的 Context 可能取消，进程退出会丢失尚未完成的工作；如果没有持久记录，也无法知道哪些任务需要恢复。本项目先提交 PostgreSQL 任务，再由独立 Worker 消费。

## 2. Asynq的至少一次投递为什么要求业务幂等？

Worker 可能已完成业务写入，却在确认消息前崩溃。队列不知道业务是否成功，只能再次投递。执行端必须识别当前版本、有效租约和已有结果，让重放收敛到同一个结果。

## 3. 为什么任务ID唯一不等于业务结果唯一？

一个业务动作可能产生多个不同消息 ID；同一消息也可能重复执行。业务唯一键限制任务行，run/token/next_run_at 限制执行，领域事务保护正文和索引，这些规则不能只靠 Asynq TaskID。

## 4. 为什么任务状态放PostgreSQL，而消息放Redis？

文档、成员权限、索引本来就在 PostgreSQL，任务状态与这些对象能用短事务协调。Redis 负责投递，丢失投递时还能从数据库恢复。这样无需让两个存储在一次跨库事务中同步提交。

## 5. 为什么202不能表示成功？

202 表示已接受并保存任务；Worker 可能尚未启动，模型也可能失败。只有任务 SUCCEEDED 且领域结果有效才表示完成。页面先显示等待，后续轮询真实状态。

## 6. 入队成功后、开始执行前Redis故障会怎样？

消息可能暂时不可见，甚至丢失；任务仍是 PENDING/RETRYING。Worker 恢复后扫描 due 任务并补发。即使原消息后来也到达，数据库的状态和租约会阻止重复执行。

## 7. 如何解释任务表兼作持久投递意图？

一条未完成任务同时表达“需要完成这项业务”和“到期应再次尝试投递”。dispatch_seq/next_dispatch_at 记录投递预留，投递结果不等于业务完成。它是专用补偿设计，不是 PostgreSQL 与 Redis 的原子事务。

## 8. 哪些错误可自动重试，哪些应立即终止？

服务暂不可用、限流、超时等有恢复可能，可以在预算内退避重试。无效文本、PDF不支持、向量数量/维度错误、依据改变或权限撤销应终止；修正文档或服务后，创建者/管理员再明确重试。

## 9. 为什么多条消息不能让总执行次数超过3？

领取在数据库事务内检查 status、run_version、next_run_at、attempts，再增加 attempts/total_attempts 并设置租约。排队消息数量不决定执行预算；自动重试每轮三次，人工重试开启新 run_version。

## 10. lease_token和run_version各防什么问题？

run_version 隔离人工重试前后的逻辑轮次；lease_token 隔离同一轮中不同实际领取者。只检查 run_version 无法识别同轮超时的旧 Worker，只检查 token 又不能让旧消息清晰失效。

## 11. 为什么租约过期后仍需在业务提交前校验？

失联 Worker 可能仍在运行，模型也可能忽略取消并迟到返回。心跳停止只是信号；真正的写入边界必须核对有效租约、版本和所有权，不能把模型返回当作写入授权。

## 12. 如何防止旧Worker的失败清理覆盖新Worker？

普通失败清理通过 context.WithoutCancel 保留原 token/run，再加独立三秒预算；数据库仍拒绝结束的租约。恢复清理另开父文档→任务事务，只清理与结束 token 匹配的中间态，不触碰新 token 或 READY。

## 13. 为什么恢复时不能重置所有PROCESSING记录？

PROCESSING 可能属于仍运行的同步请求或另一个任务。没有所有权证据就重置会造成重复执行或覆盖结果。本周只自动恢复具有匹配 task_token 的任务；历史无 token 中间态需人工查明原因。

## 14. 为什么统一父文档→任务的锁顺序？

若一方先锁文档再锁任务，另一方反过来，就可能互相等待。Submit/Claim/Cancel/Retry/Recovery 和领域发布统一顺序；心跳和投递预留只锁任务，不再回头取父锁。

## 15. 取消任务为什么不等于回滚已完成的所有步骤？

解析和索引分别提交，模型调用位于事务外。取消发生前正文可能已 READY，它不应被抹掉。取消关闭本次执行所有权，阻止后续发布，并仅清理属于该次执行的中间态。

## 16. Worker如何在API请求结束后仍有可信身份？

API 从已验证的登录身份写入 requested_by/actor_user_id。Worker 只接收任务 ID，重新读取数据库并检查 actor 是否仍为当前组织的有效成员；它不保存过期 JWT，也不信任消息携带角色。

## 17. 文件路径为什么不放到队列载荷？

路径属于服务端私有存储信息，不应该由消息指挥读取。Worker 根据可信文档记录取得对象并验证原文件 hash；最小消息既降低泄露面，也避免把队列内容变成任意文件访问参数。

## 18. Worker为什么不需要JWT签发密钥？

Worker 不接收浏览器登录请求、不签发 Token。它使用数据库中已登记的任务身份和实时成员检查，故 LoadWorker 只加载数据库、存储、模型和队列配置，减少无关秘密的传播。

## 19. 浏览器停止轮询与取消后台执行有何区别？

隐藏标签、离开页面或五分钟到期只停止查看状态，任务继续执行。点击取消会调用后端，在数据库改变状态并撤销该执行的写入资格。刷新浏览器不会代替后端取消。

## 20. W08的写操作确认与W07消息幂等为什么不能混为一谈？

W07解决文档任务重投和 Worker 失联；W08确认机制要证明用户批准了某个具体写操作，并处理参数、权限、过期、执行版本和事务幂等。消息不重复不等于用户授权，也不等于工单状态变更原子。

## 建议亲手验证

先停 Worker 再上传并提交，观察 PENDING；启动 Worker 后观察 SUCCEEDED。关闭页面再回来核对任务继续执行。使用隔离烟测观察 SIGKILL 恢复，勿拿日常数据练习强杀或改状态。最后不看答案，解释原文件 hash、正文 hash、run_version 与 lease_token 的差别。
