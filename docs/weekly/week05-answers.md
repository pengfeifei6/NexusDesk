# 第五周问题参考回答

日期：2026-11-11。AI 按整周委托整理，结合实际实现；不代表开发者已独立掌握。[周报](week05.md)记录工程验收，下面用于后续逐题复习。

## Day 1

**1. JWT 有效，为什么仍不能直接下载任意 document ID？**

JWT 只确认请求者身份。后端还要查询目标组织中的 active 成员关系，再用 org_id、document_id、deleted_at 限定对象。猜中其他组织文档 ID 不获得权限。前端隐藏入口、无法猜测的 key 都不能替代这些检查。

**2. 为什么区分“已上传”和“已解析”？**

UPLOADED 仅表示原文件和元数据保存成功。内容可能只有空白、超过正文上限，或是本周不能提取的 PDF。READY 才表示受限提取完成且正文与状态一起提交。W06 应从 READY 正文建立索引，不能直接把所有附件当作可用知识。

## Day 2

**3. 为什么事务不能回滚本地磁盘写入？怎样补偿？**

PostgreSQL 事务只管理数据库资源。本实现先保存原文件，再创建元数据；明确插入/提交失败时独立清理原文件，清理失败记 journal。提交结果未知时保留对象并待核对，防止删掉已提交元数据所引用的文件。进程崩溃仍可能留下孤儿，补偿不是跨介质原子事务。

**4. 哪些放数据库约束，哪些放 Service？**

数据库负责非空、枚举、长度/范围、key 唯一、文档一份正文、上传者和文档的复合组织外键。Service 验证当前 active 成员、删除角色、状态流转、实际文件类型与字节流限制。外键保证“成员记录存在”，不能保证成员仍 active；两层需要同时存在。

## Day 3

**5. ParseMultipartForm 的内存参数能限制整个请求吗？**

不能，它主要决定多少文件部分留在内存，剩余可能落临时磁盘。本实现不用它接收整份文件，而是 MaxBytesReader 限制整个请求，再由单文件读取上限检查实际大小，连多余部分、multipart 结尾也纳入验证。

**6. 为什么不用原文件名作路径？如何防 key 冲突？**

原文件名来自用户，可能包含目录穿越、分隔符或重复名称。它只作为受校验的展示元数据；磁盘使用服务端随机 key，并限制在私有 Root 内。即便随机碰撞，独占临时创建和最终 Link 的不覆盖语义仍会安全拒绝，不依赖“几乎不会撞”的概率保证。

**7. 不读完整文件入内存怎样计算 SHA-256？**

让 io.Copy 将受限 reader 写入 io.MultiWriter(file, sha256.New())。相同数据块同时落盘和参与 hash，io.Copy 返回真实字节数；通过 max+1 判断超限。处理 reader 错误、取消、Sync/Close 和失败清理后，才允许发布对象与元数据。

## Day 4

**8. 为什么列表与下载要分别检查权限？**

用户可以绕过列表直接请求下载，成员权限也可能在两次请求之间变化。下载必须独立检查当前成员关系和对象所属组织；不能将“曾出现在列表”当授权凭证。本实现每次查库，但不承诺对已开始传输的请求立即撤销。

**9. deleted_at 已标记但文件还在，怎样防继续下载？**

存储没有静态公开 URL。下载先从数据库查同组织、deleted_at IS NULL 的元数据，查不到就 404，不打开文件。正文接口也连接未删除父对象；只给列表加过滤而遗漏详情或下载是不够的。

## Day 5

**10. 为什么不在解析的十秒内一直持有事务？**

文件 I/O 和解析会占用时间，长事务持续占连接与行锁，拖慢并发并扩大取消影响。先用条件 UPDATE 取得处理权，事务外提取，最后短事务锁父行并一起提交正文和 READY。并发删除由最后一次锁定和可见性检查处理。

**11. PROCESSING 时进程崩溃会怎样？W07 补什么？**

内存 Context 和 defer 都不能保证在进程被杀后执行，文档可能留在 PROCESSING；当前重复处理返回 409。W07 需要持久任务、租约/心跳、超时回收、重试次数与幂等完成，并确保老 worker 不能覆盖新任务结果。本周不通过“看到 PROCESSING 就重置”制造双处理。

## Day 6

**12. 前端什么时候上传，什么时候解析？**

选文件并提交上传后调用 multipart POST，201 后进入 UPLOADED 详情；用户点击解析才调用无 body 的 process。成功后重新取得元数据和 text，失败刷新 FAILED 及固定失败码。READY 不重复解析，PDF 会明确提示本周不支持提取。

**13. 前端拦截器和后端组织校验分别做什么？**

前端 client 加 Bearer、处理超时/取消/401、映射安全提示，并阻止旧组织/旧会话的响应写回页面。后端才决定真实身份、成员角色、对象组织和动作权限。浏览器可被用户控制，因此前端校验不能作为安全边界。

## Day 7

**14. 能否不用 AI 重写带大小限制和 hash 的核心上传函数？**

本次代码由 AI 按明确委托完成，不能替开发者回答“已经会”。建议稍后不看源码重写一个只接受 reader 的版本，说明 max+1、io.Copy/MultiWriter、随机 key、Sync、失败清理，再对照 storage 测试验证。独立解释程度暂记“待自评”，不虚构学习结果。

**15. 如何演示跨组织下载失败与插入失败清理？**

用两个组织、不同成员访问同一文档下载，越界请求应 404；浏览器与真实库已有对应证据。插入失败演示使用隔离测试库的触发器，不在日常库制造故障：运行 `python3 scripts/week05-smoke.py --backend-only`，查看 B05 和 S08。后者确认 500、元数据未提交、私有文件数量未增加。

## 数据库追问与维护

**16. 为什么列表不 SELECT * 拉取正文？** 元数据列表只需名称、状态、大小和时间。正文独立表、独立授权接口按需读取，可以减少响应体、内存与跨对象内容误泄露风险。

**17. 同组织两人上传同文件可否按 hash 去重？** 技术上可设计，但要处理独立上传者权限、引用计数、删除、提交失败和信息侧漏。本周不去重，也不跨组织共享对象；相同 hash 不代表相同授权。

**18. 软删除怎样影响空间回收？** 所有普通接口隐藏对象，物理文件和正文仍占空间。未来按明确保留周期、引用核对和审计做后台清理；删除按钮当前不会立即释放磁盘。

**19. 为什么超时有时不能保证 FAILED？** 操作 Context 到期后使用独立 3 秒 Context 尽力保存失败状态；数据库仍不可用、锁长时间未释放或进程退出时也会失败。测试验证可恢复数据库中的正确更新，不等于所有故障下必然落盘。

**20. 两个 hash 为什么不同？** `sha256_hex` 对应原始上传字节；`content_sha256` 对应去 BOM、换行规范化后的正文。下载验证前者，W06 索引与提取版本使用后者。哈希用于完整性与版本识别，不替代权限、病毒扫描或可信来源判断。
