## 1. Day 1：产品范围与用户故事

### Q01：怎样用一分钟说明 NexusDesk 与普通 CRUD 管理系统的区别？

NexusDesk 面向企业内部的软件支持团队，让员工提交问题、支持人员领取处理、管理员维护组织内协作。工单从待处理到解决、关闭有明确规则，处理过程需要可追溯，组织之间的数据必须隔离。

它的后端重点包括组织与对象授权、合法状态转换、并发领取，以及工单变更和操作事件的事务一致性。例如两人同时领取一张工单，只能有一人成功；事件写入失败时，工单修改也必须回滚。这些规则让项目超出简单的表单增删改查。

当前已完成工程基础，以上工单能力属于后续目标；知识库与带来源引用的 AI 问答也在后续阶段加入。

### Q02：为什么 AI 功能不在第一周实现？

第一周需要先验证配置、HTTP、数据库、迁移和测试能否稳定工作。这些基础还没有验收时接入模型，会同时增加外部网络、密钥、费用、检索质量和流式响应等问题，排障更困难。

AI 还需要复用已经明确的用户身份、组织隔离与业务规则。先完成普通业务，后续模型和工具调用才有可信的授权入口。按现有计划，文档和 AI 能力从第 5 周以后逐步加入。

### Q03：怎样写可测试的用户故事与验收标准？

用户故事说明“谁为了什么目标需要什么能力”，验收标准说明“给定什么条件，执行什么操作，应得到什么结果”。

例如：“作为普通成员，我希望查看自己提交的工单，以了解处理进度。”可以拆成三个判断：本人访问本组织自己的工单成功；同组织其他普通成员访问该工单被拒绝；另一组织成员无法通过猜测 ID 访问它。

“权限正确”“接口正常”不能直接验收，应明确请求条件、返回结果和数据库变化。三类角色的故事及具体条件见 [需求说明](../requirements.md)。

### Q04：为什么不能相信前端传来的 user_id、org_id 和 role？

客户端可以修改请求体、URL 和请求头。前端页面隐藏按钮，也不能阻止用户直接调用接口。因此这些字段出现，并不能证明请求经过了权限审查。

后端应先验证身份凭据，得到可信的当前用户；再根据请求选中的组织查询成员关系、有效状态和角色；最后检查目标对象是否属于该组织，以及当前用户是否有权操作。`org_id` 可以表达想访问哪个组织，但必须验证。创建人等字段由后端设置，不能直接接受客户端自报的身份。

### Q05：users 与 organization_members 的区别是什么？角色为什么放在成员关系里？

`users` 表达全局账号身份，回答“你是谁”；`organization_members` 表达某个账号与某个组织的关系，回答“你是否属于这里，在这里是什么角色”。

一个用户可以在组织 A 是管理员，在组织 B 是普通成员，也可以尚未加入任何组织。若只在 `users` 中保存一个角色，就无法准确表达这种情况。

所以成员关系必须关联已有用户，但用户不一定已有成员关系；同一个用户也可以对应多条不同组织的成员关系。不要把“账号”“组织成员”和角色名中的“普通成员”混为一谈。

## 2. Day 2：架构、分层和六张表

### Q06：为什么现在选择模块化单体？它有什么代价？

当前是个人开发项目，优先目标是按期交付、方便本地调试，并把权限与事务做清楚。模块化单体可以在一个 Go API 进程中按认证、组织、工单划分职责，模块间使用普通函数调用，相关写入使用同一个 PostgreSQL 事务。

代价是模块一起发布、共享进程资源，也容易因共享数据库产生耦合。需要依靠明确接口、依赖方向、测试和审查维护边界，目录分开本身不能保证模块独立。具体比较见 [ADR-0001](../decisions/0001-modular-monolith.md)。

### Q07：一个人直接做微服务会增加什么成本？什么时候才值得拆分？

除了业务代码，还需要处理服务间通信、鉴权传播、超时、重试、日志关联、多个部署单元，以及跨服务数据一致性。原本一次本地事务可以完成的操作，拆分后可能出现部分成功，需要补偿和更多验证。

值得重新评估的证据包括：某模块确实需要独立扩容；资源或故障长期影响其他模块；独立发布节奏受到阻碍；多个团队有稳定的数据和运维责任边界。应先收集延迟、资源、积压或发布记录，比较优化与拆分成本。未来独立 Worker 可以先解决耗时任务隔离，不代表必须立刻拆成一组微服务。

### Q08：Handler → Service → Repository 怎样分工？

| 层 | 负责什么 | 工单示例 |
| --- | --- | --- |
| Handler | HTTP 参数解析、基础格式校验、获取认证上下文、映射响应 | 解析标题和描述，调用创建工单服务，返回 201 |
| Service | 授权、业务规则、状态流转、事务协调 | 校验有效成员，确定创建人和初始状态，协调工单与事件原子写入 |
| Repository | 参数化 SQL、组织过滤、结果转换 | 按 org_id 查询或写入数据，返回查询结果和存储错误 |

业务 Service 不应依赖 Gin Context，使用标准 `context.Context`，这样测试和未来工具调用都能复用规则。Repository 不负责决定 HTTP 状态码。当前第一周还没有业务 Service 或 Repository，不需要为健康检查强行添加空分层。

### Q09：六张核心表各自解决什么问题？为什么评论和事件分开？

| 表 | 作用 | 当前阶段 |
| --- | --- | --- |
| organizations | 组织根实体，提供租户标识 | 第一周已建表并验证 |
| users | 全局账号身份 | 第二周计划 |
| organization_members | 用户与组织的关联、组织内角色和有效状态 | 第二周计划 |
| tickets | 工单当前内容、状态、处理人与版本 | 第三周计划 |
| ticket_comments | 用户和处理人员之间的沟通内容 | 第三周计划 |
| ticket_events | 创建、领取、解决等业务变化记录 | 第三周计划 |

评论回答“大家沟通了什么”；事件回答“谁在什么时候改变了什么”。普通评论不能伪造为领取或关闭记录，业务事件由相应操作生成。工单修改与事件写入放在同一事务中，避免当前状态已经变化却没有对应历史。

### Q10：怎样唯一标识租户？主键、外键、org_id 和时间字段分别有什么用？

`organizations.id` 是组织的稳定标识，组织名称用于展示，可以重名或变化，不适合作为租户主键。

- 主键唯一标识一条记录；成员表的 `(org_id, user_id)` 联合主键防止同一用户在同一组织重复加入。
- 外键约束引用对象必须存在。例如成员引用用户和组织，避免出现找不到所属对象的关系。
- `org_id` 表达业务数据属于哪个组织。后续查询与写入必须使用经过授权的组织上下文限定范围。
- `created_at` 记录创建时间；需要 `updated_at` 的表由写入代码或明确的数据库机制更新，不能假设它会自动变化。

数据库约束、组织过滤和业务授权分别承担不同职责，需要一起使用。

### Q11：有 org_id 或外键，是不是就保证了组织权限？

不能。普通外键只能验证引用存在；设计中的组合外键可以进一步验证工单、作者和组织关系一致。但它们不会自动判断当前请求者是谁、成员是否停用、角色是否允许该操作。

例如，数据库里组织 A 的工单确实存在，不代表组织 B 的用户可以读取它。后端仍需验证身份与成员资格，查询限定 `org_id`，普通成员还要限定自己可见的对象范围。外键是数据一致性保护，完整授权需要在业务入口执行。

## 3. Day 3：工程、配置与协作规则

### Q12：Go Module 解决什么问题？go.mod 与 go.sum 有什么区别？

Module 为一组 Go 包提供统一的模块路径和依赖管理边界。本项目路径为 `github.com/pengfeifei6/NexusDesk`，内部导入沿用同样的大小写。

`go.mod` 声明模块路径、Go 版本要求和依赖版本；`go.sum` 保存依赖模块及其 go.mod 文件的校验值，用于检查下载内容。两者都应提交。go.sum 不是传统的依赖锁文件，版本选择主要由 go.mod 和依赖图决定。直接依赖被项目代码使用，间接依赖通常由其他依赖引入；最终结果应结合实际引用和 `go mod tidy` 判断。参见 [Go Module 官方参考](https://go.dev/ref/mod)。

### Q13：AGENTS.md 能做什么，不能做什么？为什么第一周默认 REVIEW_ONLY？

本仓库的 [AGENTS.md](../../AGENTS.md) 记录项目阶段、可修改范围、配置保护、验证要求和禁止自动执行的操作，帮助协作者按一致方式工作。

它是仓库协作说明，不能充当操作系统访问控制，也不能保证秘密绝对不可读取。实际权限仍由运行环境和工具访问控制决定。

第一周默认只读审查，是为了让开发者先实现与理解基础，再借助 AI 查错。实际协作中，开发者已明确委托 AI 生成多个文件并完成工程验证，应如实记录这项授权与工作归属。它不等于后续所有修改、提交或部署都自动获得授权。

### Q14：为什么 .env.example 与 .env 要分开？怎样确认凭据没有进入 Git？

`.env.example` 是可共享的配置模板，包含变量名和占位值；`.env` 保存开发者本机的实际值，必须被忽略。这样其他人知道需要配置什么，又不用共享同一份密码。

可以用 `git check-ignore .env` 检查忽略规则，再用 `git ls-files -- .env` 检查它是否已经被跟踪。忽略规则不能自动取消已有跟踪，也不能清除旧提交中的内容。提交前还要审查暂存内容，不能只看文件是否出现在 `git status`。

这里给出的是检查方法，不表示本次读取过真实配置。若凭据曾泄露，需要更换凭据并处理泄露记录，单加忽略规则不能让旧凭据失效。

### Q15：为什么写了 .env，os.Getenv 仍然读不到？

`os.Getenv` 读取进程环境变量，不会自动打开项目目录里的 `.env`。本地运行前需要由开发者把配置加载到启动终端，或由明确的启动工具注入；应用继承该进程环境。

新终端没有自动继承另一个终端后来设置的变量。Compose 为替换配置而加载 `.env`，也不会反过来修改宿主机终端或 Go 进程的环境。当前 Linux / Bash 操作以 [README](../../README.md) 为准，第一周应用没有内置 dotenv 加载器。

### Q16：为什么不一次创建全部目录？如何理解 Git 提交的边界？

只创建当前有实际用途的文件，能让职责与开发进度对应，避免空接口和目录被误认成已经实现的功能。第一周不需要先建 Worker、RAG、Agent 或前端模块。Git 本身也不记录真正的空目录。

一次提交应保存可解释的一组变更。提交前核对工作区、未跟踪文件和暂存差异，确认不含秘密或无关文件。不要为凑阶段数量制造空提交；也不要把 AI 已生成文件等同于已提交。第一周已有提交与工作区成果的区别见 [周报第 12 节](week01.md#12-git-整理与当前基线)。

## 4. Day 4：HTTP 服务、配置与生命周期

### Q17：main、Router 和 Handler 各自负责什么？为什么 cmd/api 不放核心业务？

`main` 是应用入口，组合配置、数据库与 HTTP 服务，并管理进程信号和退出；Router 按请求方法和路径选择处理链；Handler 处理具体 HTTP 请求并写出响应。

核心业务放在入口，会把启动配置、数据库操作和权限规则混在一起，难以独立测试，也不利于其他入口复用。后续工单状态与授权放在 Service，入口负责把依赖组装起来。

本项目的 `main` 建立信号 Context，`run` 加载配置并验证数据库，再由 `runHTTP` 管理监听与退出。参见 [启动代码](../../cmd/api/main.go)。

### Q18：Gin 如何处理 GET /healthz？为什么它返回成功不等于全部系统正常？

当前 [NewRouter](../../internal/platform/httpserver/router.go) 创建 Gin Engine，注册 Recovery 中间件，并通过 `router.GET` 绑定 `/healthz`。请求的方法和路径匹配后，Handler 使用 `c.JSON` 返回 HTTP 200 和 `{"status":"ok"}`。

它是固定响应的存活检查，不会在每次请求查询数据库。API 启动前做过数据库 Ping，只能证明当时连通；后续数据库故障，健康接口仍可能返回 200。它也不能证明组织表存在、迁移已完成或未来业务可用。需要依赖就绪检查时应另行设计，当前没有 `/readyz`。

### Q19：配置和启动失败应该怎样被感知？怎样排查 404、端口占用和数据库失败？

配置缺失或非法时尽早返回能定位变量的错误，不输出密码；数据库不可达时在 HTTP 监听前失败；端口监听失败时返回明确错误。顶层记录错误并以非零退出码结束，让终端、脚本和未来部署工具能发现失败。

| 现象 | 建议验证顺序 |
| --- | --- |
| `/healthz` 返回 404 | 确认 GET 方法、路径、访问端口、实际运行的进程及路由注册 |
| 地址格式错误 | 检查当前进程环境里的 HTTP_ADDR 是否符合 host:port |
| 端口已占用 | 查明占用进程，核对自己的监听配置，避免随意结束不明进程 |
| 数据库连不上 | 区分容器未就绪、端口错误、认证失败、数据库不存在和超时 |

当前配置代码允许 HTTP 端口 0，用于让系统分配临时测试端口；正常手动运行采用明确端口。不能把它当成数据库端口的有效值，当前 DB_PORT 校验范围是 1～65535。

### Q20：为什么要 Context、超时和优雅退出？

Context 传递取消信号与截止时间，使数据库调用等操作可以停止无意义的等待。只有把它传入支持取消的调用，取消才会产生作用；创建 Context 本身不会停止任意代码。

当前数据库启动验证有 5 秒上限。收到 SIGINT 或 SIGTERM 后，应用 Context 被取消，HTTP 使用另一个独立、最多等待 5 秒的 Context 执行 Shutdown，随后释放连接池。不能把已经取消的 Context 直接作为退出等待条件，否则可能没有机会等待在途请求。

超时是当前实现的等待边界，不是请求必然在某个精确毫秒退出的保证。具体实现见 [main.go](../../cmd/api/main.go) 和 [postgres.go](../../internal/platform/database/postgres.go)。

## 5. Day 5：PostgreSQL、连接池和迁移

### Q21：Docker PostgreSQL 与宿主机 Go API 怎样连接？为什么不能直接用 db？

当前 Compose 把容器的 5432 端口映射到宿主机的 `127.0.0.1:${DB_PORT}`。宿主机上的 Go API 使用 `DB_HOST=127.0.0.1` 和映射后的端口连接，用户名、密码、数据库名与 SSL 模式来自环境变量。

`db` 是 Compose 服务名，供同一 Compose 网络中的容器访问。当前 API 在宿主机运行，不应假定宿主机能解析这个名字。如果以后 API 也进入同一容器网络，需要重新区分容器内服务地址和宿主机映射地址。

当前端口绑定到回环地址，适合本地开发。连接关系与配置见 [compose.yaml](../../deploy/compose.yaml)。

### Q22：连接池是不是一条永久连接？为什么创建池后还要 Ping？

连接池管理多条可复用的数据库连接，调用方按需获取、使用并归还。它减少重复建立连接的开销，也需要合理的容量和生命周期管理；不是一条永远不会断开的连接。

创建池成功不等于实际连通，必须执行 Ping 等操作才能验证连接。当前 `database.Open` 在返回前实际 Ping，失败则关闭池；成功后由应用负责在 HTTP 退出后关闭。调用数据库仍要处理运行期间的连接错误。参见 [pgxpool 官方 API](https://pkg.go.dev/github.com/jackc/pgx/v5/pgxpool)。

### Q23：为什么需要 migration，而不是手工建表？Up、Down 和版本表是什么？

手工建表容易漏记步骤，其他环境难以复现，也难以审查结构变化。migration 把变更写成按版本执行的 SQL，与代码一起保存。

Up 应用该版本结构变化；Down 描述撤销方式。Goose 通过版本表记录迁移状态，Status 用于查看状态。正常由 Goose 管理的已应用迁移，再次 Up 不会直接重复执行同一版本。

版本记录不是数据库结构的实时审计，手动改表仍可能造成漂移。执行过、已经共享的迁移应通过新增文件演进，保留 `00001_create_organizations.sql` 的历史含义。API 启动只验证连接，不会自动运行迁移。

### Q24：为什么 organizations.id 使用 BIGINT？Identity 与主键有什么区别？

BIGINT 是容量较大的整数类型。本项目沿用手册，使用统一的整数实体标识，便于关联和学习；这不是在声称当前流量需要如此大的容量，也不表示它在所有场景都优于 UUID。

`GENERATED BY DEFAULT AS IDENTITY` 在没有显式提供 ID 时，使用隐式序列生成值。`BY DEFAULT` 允许显式指定值，因此唯一性仍由 `PRIMARY KEY` 保证，不能把 Identity 本身当作唯一约束。序列可能有间隙，事务回滚也不保证号码回收，不能要求 ID 连续。参见 [PostgreSQL 17 Identity 文档](https://www.postgresql.org/docs/17/ddl-identity-columns.html) 和 [序列函数文档](https://www.postgresql.org/docs/17/functions-sequence.html)。

### Q25：NOT NULL 能阻止空字符串吗？时间为什么用 TIMESTAMPTZ？

`NOT NULL` 只禁止 SQL NULL，不能禁止空字符串或全空格。例如当前组织表的 `name VARCHAR(100) NOT NULL` 仍不能单独满足未来“名称必须有有效内容”的规则，需要明确的应用校验和适用约束。

`TIMESTAMPTZ` 表示确定的时间点，适合记录创建和变更事件。PostgreSQL 将其按 UTC 保存，并按会话时区显示；它不会保留最初输入的时区名称。当前 `created_at DEFAULT NOW()` 在插入未提供时间时使用数据库时间，NOW() 对应事务开始时间，并非每次调用重新读取墙钟。参见 [PostgreSQL 17 时间类型文档](https://www.postgresql.org/docs/17/datatype-datetime.html) 和 [时间函数文档](https://www.postgresql.org/docs/17/functions-datetime.html)。

### Q26：为什么 Down 会丢数据？down 与 down -v 又有什么区别？

本项目首条迁移的 Down 执行 `DROP TABLE organizations`，会删除表及表内数据。再次 Up 只能重新建立结构，不能恢复已经删除的业务记录。因此回滚实验只应在确认可丢弃的测试库中进行。

Compose 的 `down` 处理容器与网络，默认保留命名数据卷；`down -v` 会进一步删除 Compose 声明的命名卷和所连接的匿名卷，external 卷不由它删除。两组命令作用不同，但都不能不看目标环境直接执行。保留卷也不等于已经有了备份。参见 [Compose down 官方说明](https://docs.docker.com/reference/cli/docker/compose/down/)。此处解释原理，没有执行任何回滚或删除操作。

### Q27：healthy、Ping 成功与迁移完成分别证明什么？

| 信号 | 能说明什么 | 还不能证明什么 |
| --- | --- | --- |
| 容器 healthy | 当前健康命令 pg_isready 判断服务处于可接受连接的状态 | 应用凭据正确、业务表存在 |
| 应用 Ping 成功 | 应用使用配置，在当时成功访问数据库 | 迁移已完成、后续不会断连 |
| Goose 状态与实际查表 | 迁移记录和所检查的表结构符合预期 | 未来业务规则与权限正确 |
| `/healthz` 返回 200 | HTTP 健康路由能响应 | 数据库持续健康、全部业务可用 |

验收需要组合这些证据。例如，只有容器进程在运行，仍可能没有完成数据库初始化。pg_isready 的检查语义见 [PostgreSQL 17 官方说明](https://www.postgresql.org/docs/17/app-pg-isready.html)。

### Q28：密码改了为什么仍认证失败？为什么日志不能直接输出 DSN？

官方 PostgreSQL 容器的初始化环境变量通常只在空数据目录首次初始化时创建用户和密码。使用已有卷时，只改本地 DB_PASSWORD，不会自动修改数据库中已有账号的密码。参见 [官方镜像的环境变量说明](https://hub.docker.com/_/postgres)。

应核对连接目标、卷是否已有数据和账号配置，再按需要通过正规的数据库操作修改密码。不能把删除数据卷当作默认修复。

DSN 可能含用户名与密码，部分底层错误也会带完整连接信息。当前连接代码使用 URL 编码处理特殊字符，对外返回经筛选的错误信息，避免把整个配置结构、URL 或解析错误原文写入日志。真实配置只在开发者本机维护。

## 6. Day 6：测试、质量检查与审查

### Q29：go test、go vet、go build 分别做什么？race 和格式检查又有什么用？

| 检查 | 主要作用 | 局限 |
| --- | --- | --- |
| `go test ./...` | 运行各包测试，验证断言描述的行为 | 未覆盖的行为仍可能有错 |
| `go vet ./...` | 静态检查一类可疑写法，例如格式化参数问题 | 不是完整业务或安全证明 |
| `go build ./...` | 检查包能否编译，命令能否构建 | 不会替代运行测试和迁移 |
| `go test -race ./...` | 检测本次执行路径中发生的数据竞争 | 没执行到的路径不能由此保证 |
| `gofmt` / `go fmt` | 统一 Go 源码格式 | 格式正确不代表逻辑正确 |
| `git diff --check` | 检查差异中的尾随空白等格式问题 | 未跟踪文件和干净 checkout 中已提交内容不靠它检查 |

对第一周，以上检查加上 HTTP、数据库和进程烟测共同形成验证证据。不能把“能编译”写成“功能全部正确”。

### Q30：httptest.NewRequest、NewRecorder 与真实 HTTP 请求有什么区别？

`httptest.NewRequest` 构造供服务端测试使用的请求；`NewRecorder` 在内存中记录 Handler 写出的状态码、响应头和响应体。把两者传给 Router 的 `ServeHTTP`，即可测试路由响应，不需要监听端口。参见 [Go httptest 文档](https://pkg.go.dev/net/http/httptest)。

本项目用这种方式检查 200、JSON Content-Type，以及可解析且只有 `status=ok` 的固定响应，见 [router_test.go](../../internal/platform/httpserver/router_test.go)。

真实进程配合 HTTP 客户端，还能检查端口监听、启动配置、数据库接入和信号退出。两种验证覆盖不同边界。另外，httptest 包中的 `NewServer` 会真实启动测试服务，不能把整个 httptest 包都理解为“不使用网络”。

### Q31：测试失败时应该怎样处理？为什么不能直接删除断言？

先保留失败输出，确认失败用例、前提条件和可复现方式，再提出能被实验区分的原因。例如数据库集成测试失败，需要区分代码错误、配置错误、服务未启动和迁移缺失。

修复后重跑原来失败的用例，并运行相关回归。若断言确实与需求不符，应说明需求依据后修改；不能仅为得到绿色结果而删掉权限检查、跳过失败或改成恒真断言。

### Q32：怎样判断 Review 建议是否应该采纳？第一周实际处理了什么？

建议应给出文件位置、触发条件、影响与验证方法。已复现的问题优先修复；尚未验证的风险补实验；主观偏好结合当前范围权衡，不需要全部照单接受。

第一周新发现是：CI 在干净 checkout 中使用 `git diff --check`，由于没有工作区差异，不能检查本次已提交变更。已移除这个无效步骤，保留 Go 格式、race、vet 和 build。数据库黑洞连接超时、连接途中取消的测试缺口也已补齐；真实进程烟测验证收到响应后的信号退出。详情见 [审查报告](../reviews/week01-review.md)。

### Q33：为什么普通测试中有 Skip？本地通过能否证明远程 CI 通过？

真实数据库集成项默认跳过，让普通单测不依赖本地数据库和真实 `.env`。独立烟测显式开启集成测试，在自己的临时数据库中验证。Skip 是没有运行该项，不能计为通过。

2026-11-09 的 [测试摘要](evidence/week01-test-summary.json) 记录：4 个包通过，顶层测试 14 通过、0 失败、1 跳过；被跳过的是 `TestOpenPostgresIntegration`，它在 [完整烟测](evidence/week01-clean-reproduction.log) 中另行执行通过。

GitHub Actions 文件已准备，本地等效命令和静态检查已有记录；远程工作流尚未触发，不能宣称云端通过。

## 7. Day 7：复现、真实复盘与第二周交接

### Q34：怎样证明 README 足以复现？“从零”应该怎样准确表达？

把运行源码和必需配置放到干净项目目录，不复制真实 `.env`、旧构建产物或未记录脚本，按文档准备配置、启动数据库、应用迁移、运行 API，再验证健康响应和质量命令。

第一周已经由 AI 在 `/var/tmp` 干净目录完成一次实际验证，还验证了保留数据卷停止、重启后表和迁移版本仍然存在。但这次复用了当前主机工具、模块缓存和本地镜像，所以应称为“干净项目目录复现”，不能据此宣称一台全新机器也已安装验证。见 [演示摘要](week01-demo.md)。

### Q35：本周有哪些真实排障案例？怎样写“现象—证据—根因—验证”？

可使用第一周归档的干净快照构建问题，写法如下。

| 环节 | 参考记录 |
| --- | --- |
| 现象 | `/tmp` 下的快照数据库步骤通过，但 API 构建报 `error obtaining VCS status` |
| 证据 | 相同源码在原仓库能构建；首次失败日志被保留；祖先 `/tmp/.git` 存在但不能识别为有效仓库 |

| 处理 | 保持他人文件不动，把快照放到祖先没有该标记的 `/var/tmp` |
| 验证 | 同一源码在新位置完成数据库、构建、HTTP 与退出信号验证 |

原始材料见 [首次失败日志](evidence/week01-clean-reproduction-attempt1.log) 和 [成功日志](evidence/week01-clean-reproduction.log)。这个案例由 AI 排查，不能写成开发者独立解决的个人经历。

对于“我独立解决了什么”“我掌握了什么”等个人问题，参考答案只能提供记录方式，内容应由开发者根据实际经历填写。现有 [周报第 7 节](week01.md#7-个人学习与排障记录) 继续保留待补充状态。

### Q36：第一周完成和“已经掌握”有什么区别？进入第二周前应该保留什么？

工程完成要有代码、实际运行和验证证据；个人掌握需要能够解释、复现并进行小范围独立修改。AI 已生成和验证，不自动证明开发者能独立完成。

进入第二周应保留第一周启动、健康检查、连接池、迁移与测试，新增表使用增量迁移。首先协调新手册与旧设计中的角色、成员可见性和组织创建差异，再建立用户、组织成员、认证和授权。

## 8. 其他常见故障的参考回答

| 手册中的问题 | 对应回答 |
| --- | --- |
| Go 命令不存在 | 检查安装位置、PATH 和当前终端，必要时重新打开终端；先确认环境，避免直接执行来历不明的安装脚本 |
| import 失败 | 核对 Module 路径大小写、文件所在包、依赖版本和下载网络；确认实际引用后使用 go mod tidy，不靠删除 go.sum 碰运气 |
| Docker 无法连接 | 区分 CLI 可调用与守护进程可访问，检查服务、当前上下文和权限；不用删卷处理连接问题 |
| PostgreSQL 无法启动 | 检查 Compose 状态、端口冲突和经脱敏的容器日志；已有卷与初始化配置也要区分 |
| migration 失败 | 核对目标数据库、Goose 注解、SQL 错误及版本状态；确认原因前不强制回滚重要库 |
| AI 改动过多 | 结合任务范围和 Diff 判断，要求缩小改动并保留现有工作；不因工具声称完成就直接接受或提交 |

以上是排查入口，具体根因需要对应环境的证据。第一周已有问题及处置集中在 [周报](week01.md) 和 [审查报告](../reviews/week01-review.md)。
