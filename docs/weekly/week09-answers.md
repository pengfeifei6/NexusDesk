# 第九周问题参考答案

这是结合当前实现由 AI 整理的参考回答，供后续对照代码复习，不代表你已独立掌握。先看 `cmd/api/main.go` 注入，再沿两个 Service.List → cache.List → Repository.List 阅读。

## 手册能力检查十问

### 1. 为什么缓存 Key 必须包含组织 ID？

同样的 page=1、status=OPEN 在不同组织代表不同数据。没有 org_id，后到请求可能命中另一个组织的结果。数据库 SQL、Key 和缓存条目三处都要保留组织边界，不能只把 Key 修对就省掉 SQL WHERE。

### 2. 结果受角色权限影响时，只包含组织 ID 是否安全？

不安全。假如管理员看全组织、普通成员只能看自己，同组织下就有两种可见范围。要让权限策略、SQL 和 Key 的 scope 一致，必要时加可信用户 ID。本项目当前 active admin/member 都看本组织所有工单与文档，所以使用 `active-members-all`，但每次仍查数据库成员状态。将来的产品规则变化必须同时修改缓存设计。

### 3. 为什么失效应发生在提交之后？

先删缓存、后提交时，另一个读者可能查到尚未改变的数据库，再把旧结果填回来；写事务还可能回滚。本项目把版本增加放在数据库事务中，其他连接只有提交后才能看到新版本。事务内写版本不是提前暴露失效：外部可见性由数据库提交控制。

### 4. Redis 不可用时为什么不能无限重试？

缓存的目的是减少查询成本。无限重试会占住 HTTP 请求、连接和协程，把辅助组件故障变成全站故障。当前每操作默认 100ms、禁自动重试；列表回源数据库。回源也有成本，因此大流量下还需容量评估，不能把“能降级”理解为“任何流量都能撑住”。

### 5. 固定窗口限流有什么边界问题？

用户可在窗口末尾用完额度，紧接着在新窗口再次用完，短时间内形成接近两倍额度的突发。本项目窗口从首次请求开始计算，仍存在相邻窗口突发。它限制窗口总次数，并不保证均匀速率；已有 AI 两并发上限继续保留。需要平滑速率时再考虑滑动窗口或令牌桶。

### 6. Redis 计数和判断为什么需要原子执行？

两个请求若分别 GET，可能同时看到还剩一次，各自都放行；INCR 与 EXPIRE 分开还可能留下永不过期的计数。短 Lua 脚本把检查、计数、首次设置 TTL 放在一次原子操作里，所有 API 实例共享同一配额事实。[Redis Lua 原子执行说明](https://redis.io/docs/latest/develop/programmability/eval-intro/)

### 7. EXPLAIN 估算行数和实际行数差很多说明什么？

可能是统计信息陈旧、数据分布偏斜、列之间相关、表达式难估算，或 generic plan 无法利用本次参数。先确认实际参数、数据规模和 ANALYZE 状态，再定位出现误差的节点；不能看到误差就直接增加索引或强制关闭顺序扫描。

### 8. 组合索引的列顺序为什么重要？

本周 priority 列表先固定 org_id 和 priority，再按 created_at/id 排序，因此 `(org_id,priority,created_at DESC,id DESC)` 可直接读取所需区间和顺序。若把不固定的 priority 放在组织后却拿它服务无 priority 筛选的全列表，时间顺序就不再自然连续，所以原组织/时间索引仍有用途。

### 9. LIMIT/OFFSET 大页码为什么慢？

数据库仍要找到并跳过 offset 行，LIMIT=20 不意味着只读 20 行。稳定排序只解决并列排序的不确定性，不消除深页成本，也不保证两次请求间新增数据不会移动页边界。keyset/cursor 可利用上一页最后的 created_at/id，但需要改 API 协议，本周保留现有分页。

### 10. 如何证明优化有效而不是偶然波动？

固定数据和参数，先记录基线，说明机器、PG 版本、热/冷条件，多次运行并比较中位数；同时看扫描行数、buffer、是否有额外排序等结构变化。再验证优化前后结果相同。本周保留 9 次原始 JSON 计划，而不是只展示最快一次。知识列表 auto 原本就有好计划，小数值差异不应宣传为稳定倍数提升；generic 场景的扫描下降有更明确依据。

## 看代码时常见的八个问题

### 11. 数据库版本查询还存在，缓存有什么用？

版本查询按 `(org_id,domain)` 主键只取一个整数；它比扫描、筛选、分页并读取大量工单正文便宜。缓存并不适合所有小表/小查询，有可能净收益很小，所以既保留缓存开关，也说明额外点查与写版本的成本。

### 12. 为什么不直接 DEL 所有列表 Key？

列表有状态、优先级、分页等许多变体，逐个删除很难完整覆盖；KEYS/全局清空还会影响 Asynq。组织/领域版本让所有旧变体自动不可达，并由 TTL 回收。版本存在 PG 可覆盖 Redis 中断期间的写入以及 Worker/AI 外层事务。

### 13. Redis 恢复以后怎么避免旧缓存回来？

读者取 PG 当前版本拼 Key。停机期间写入已经增加版本，恢复的 Redis 旧 key 属于旧版本，不能再命中。数据库备份恢复导致版本倒退属于另一种运维情形，需要停 API 并更换缓存命名空间或清理确认属于本项目的缓存前缀，不能 FLUSHDB 清掉队列。

### 14. 缓存缺失、缓存故障和坏 JSON 有什么区别？

缺失是正常情况，故障可能是网络/超时/Redis 内存问题，坏 JSON 表示值不可用。用户最终都可以得到数据库结果，但运维计数需要区分，才能知道命中率低是正常 TTL 还是依赖异常。不能将其中任何一种误当作“数据库没有记录”返回空列表。

### 15. 为什么普通查询回源，AI 限流却在 Redis 故障时拒绝？

普通列表缓存失败可以直接用数据库完成原业务；AI 配额失败若全部放行，会失去对付费模型调用的限制。因此本项目选择保守拒绝：AI 发送返回 503，列表和工单写入仍可用，历史及确认/拒绝也不受此额度控制。503 是配额依赖不可用，429 是已超过配额。

### 16. 前端隐藏发送按钮是否就实现了限流？

没有。用户可以直接调用 HTTP，也可以开多个页面。服务端根据已验证身份与组织实施 Redis 计数，前端只负责明确提示和保留未发送输入，不自动重试。会话归属也先验证，不能靠伪造别人的会话 ID 消耗对方额度。

### 17. 更新成功但是 Redis SET 失败，应该给用户报错吗？

业务写入是否成功由数据库提交决定。缓存不是事实源，缓存写失败不能把已经创建的工单伪装成创建失败，否则用户重试可能重复操作。当前写路径根本不依赖 Redis；读回源后的 SET 失败也只记录安全计数并返回已查到的数据。

### 18. 第九周是否已经适合公网生产？

这周完成的是指定缓存、一个高成本接口限流和两条查询优化。登录防暴力破解、公开入口代理策略、容量规划、备份恢复演练、可观测性平台等不能由本周局部验收替代。应用仍按项目原约定绑定回环地址。下一周应按第十周手册继续检索评测和 RAG 增强，不把未做的能力写成已完成。
