# NexusDesk 工作流依赖与触发事件学习指南

更新日期：2026-11-11。

这份文档不是按文件夹介绍代码，而是按“**谁触发 → 依赖谁 → 改变什么状态 → 是否产生事件或后续任务**”来阅读。建议把本文和代码左右分屏，按照每个工作流给出的文件顺序逐个定位函数。

## 一、先建立总图：触发源只有几类

```text
浏览器按钮 / 页面加载
        │
        ▼
Vue View → composable → client.fetch
        │ HTTP + Bearer Token
        ▼
Gin Router → RequireUser → Handler.scope
        │ 参数、组织成员、输入校验
        ▼
Service
   ├─ 同步事务：Repository 更新数据 + 审计事件，一起提交
   └─ 异步任务：写入 PostgreSQL 任务状态
                         │
                         ▼
              Worker 每 2 秒扫描到期任务
                         │
                         ▼
                  Redis / Asynq 投递
                         │
                         ▼
              Worker.Execute → 文档处理 → RAG 索引
```

### 依赖的四个层次

| 层次 | 具体依赖 | 阅读位置 |
| --- | --- | --- |
| 入口依赖 | Vue 路由、按钮、页面生命周期 | [`web/src/views/`](../web/src/views/)、[`web/src/components/`](../web/src/components/) |
| HTTP 依赖 | Gin 路由、认证中间件、JSON/Multipart 输入 | [`internal/platform/httpserver/router.go`](../internal/platform/httpserver/router.go)、各模块 `handler.go` |
| 业务依赖 | Service 注入的 Repository、其他 Service、成员查询 | 各模块 `service.go` |
| 基础设施依赖 | PostgreSQL、私有文件目录、Redis、Ollama/DeepSeek | [`cmd/api/main.go`](../cmd/api/main.go)、[`cmd/worker/main.go`](../cmd/worker/main.go) |

先看 [`cmd/api/main.go`](../cmd/api/main.go) 和 [`cmd/worker/main.go`](../cmd/worker/main.go)，确认对象是在哪里创建并传入的；再从具体 Handler 往下追。不要把“文件名叫 repository”理解成它一定是独立的 Repository：例如 `jobs.Service` 直接持有数据库连接池。

## 二、事件在本项目中是什么意思

这里的“事件”有两种，不要混为一个事件总线：

1. **业务审计事件**：例如工单领取产生 `TICKET_ASSIGNED`。它和工单更新在同一数据库事务里，提交成功才可见；失败会一起回滚。
2. **异步任务触发**：例如文档提交异步处理后，任务行由 Worker 扫描并投递到 Redis/Asynq。它不是浏览器直接调用 Worker，也不是数据库自动触发器。

因此排查一个工作流时，先问两个问题：

- 这次变化是否需要和主数据强一致？如果需要，看 `Service.write`、事务 Repository 和 `InsertEvent`。
- 这次操作是否耗时或可重试？如果是，看 `jobs` 状态机、`Dispatch`、队列 Payload 和 `Execute`。

## 三、例一：领取工单——按钮触发同步事务和审计事件

### 阅读顺序

1. [`TicketDetailView.vue`](../web/src/views/TicketDetailView.vue)：找到“领取工单”按钮及点击处理函数。
2. [`web/src/composables/desk.ts`](../web/src/composables/desk.ts)：沿着领取动作看请求路径和 `expected_version` 的来源。
3. [`web/src/lib/client.ts`](../web/src/lib/client.ts)：确认请求统一加 Bearer Token、编码整数，并把 HTTP 错误转成 `ApiError`。
4. [`internal/platform/httpserver/router.go`](../internal/platform/httpserver/router.go)：确认 API 前缀 `/api/v1`，再看工单模块注册到受保护路由组。
5. [`internal/auth/middleware.go`](../internal/auth/middleware.go) 的 `RequireUser`：验证 JWT，并把当前用户放进 Gin Context。
6. [`internal/ticket/handler.go`](../internal/ticket/handler.go) 的 `scope`、`claim`：解析组织、工单、输入版本，并调用 Service。
7. [`internal/ticket/service.go`](../internal/ticket/service.go) 的 `Claim`、`write`、`audit`：复查成员关系、开启事务、执行业务变化并写审计事件。
8. [`internal/ticket/repository.go`](../internal/ticket/repository.go) 的 `ClaimTicket`、`InsertEvent`、`Commit`：查看数据库条件更新和事件落库。

### 触发和依赖链

```text
点击领取
  → POST /api/v1/organizations/:orgID/tickets/:ticketID/claim
  → RequireUser
  → handler.scope / claim
  → service.Claim
  → service.write 开事务并复查 active membership
  → ClaimTicket 条件 UPDATE
  → audit 写 TICKET_ASSIGNED
  → Commit
  → 返回新工单，前端重新加载详情、评论和事件
```

### 必须看懂的三个约束

- **权限约束**：前端的“可领取”只是 UX；后端 `member`/`FindActiveMembership` 才是最终授权。
- **并发约束**：`ClaimTicket` 同时要求组织、`OPEN` 状态、无受理人、旧 `version` 匹配。两个用户同时领取时，只有一个条件更新成功。
- **一致性约束**：领取更新和 `TICKET_ASSIGNED` 事件共用一个事务。不能只更新工单后再单独写事件。

修改领取逻辑时，至少同时检查 View/composable、Handler、Service、条件 SQL、审计事件和冲突状态码。

## 四、例二：上传文档——上传和异步提交是两个触发点

### 阅读顺序

1. [`KnowledgeDetailView.vue`](../web/src/views/KnowledgeDetailView.vue) 或 [`KnowledgeListView.vue`](../web/src/views/KnowledgeListView.vue)：找到文件选择、上传和“提交异步处理”的入口。
2. [`web/src/composables/knowledge.ts`](../web/src/composables/knowledge.ts) 的 `upload`、`process`：确认上传请求和任务提交请求是分开的。
3. [`web/src/components/AsyncJobPanel.vue`](../web/src/components/AsyncJobPanel.vue)：看任务提交、刷新、重试、取消和轮询。
4. [`internal/knowledge/handler.go`](../internal/knowledge/handler.go) 的 `upload`：校验 multipart，只接收一个文件，并调用 `knowledge.Service.Upload`。
5. [`internal/knowledge/service.go`](../internal/knowledge/service.go) 的 `Upload`、`Process`：看文档元数据、私有文件和正文状态如何变化。
6. [`internal/jobs/handler.go`](../internal/jobs/handler.go) 的 `submit`、`list`、`retry`、`cancel`：确认任务 API 的入口和状态码。
7. [`internal/jobs/service.go`](../internal/jobs/service.go) 的 `Submit`、`Retry`、`Cancel`：看 PostgreSQL 中任务状态如何创建或转换。
8. [`internal/jobs/repository.go`](../internal/jobs/repository.go)：查看任务行、版本、重试和取消条件。

### 两次请求的边界

```text
选择文件
  → POST /knowledge/documents
  → 保存文件和文档记录
  → 返回 document

提交异步处理
  → POST /knowledge/documents/:documentID/jobs
  → 创建或复用 knowledge_jobs 任务行
  → 返回 PENDING/RETRYING 等任务状态
  → 页面开始轮询 GET /knowledge/documents/:documentID/jobs
```

上传成功不等于正文已经提取，任务提交成功也不等于索引已经完成。`knowledge.ts` 特意把上传失败和异步提交未确认分开处理，避免用户重复上传同一个文件。

### 页面轮询不是执行器

[`AsyncJobPanel.vue`](../web/src/components/AsyncJobPanel.vue) 每约 2 秒读取任务状态，但它只负责展示。真正的执行触发来自 Worker 的 `Dispatch`，所以：

- 只启动 API：可以上传、创建任务、查询任务，但没有 Worker 执行；
- 只启动 Worker：没有 API 就无法从页面提交任务；
- 页面关闭后，任务仍可继续，因为任务状态保存在 PostgreSQL，执行在 Worker 进程中。

## 五、例三：Worker 如何把数据库任务变成执行事件

### 阅读顺序

1. [`cmd/worker/main.go`](../cmd/worker/main.go) 的 `run`：看 Worker 组装数据库、文档 Service、RAG Service、队列客户端和 Asynq Server。
2. [`internal/jobs/service.go`](../internal/jobs/service.go) 的 `Dispatch`：看每 2 秒扫描哪些任务、如何预留 dispatch 序号。
3. [`internal/platform/taskqueue/asynq.go`](../internal/platform/taskqueue/asynq.go) 的 `Enqueue`：看 Payload 只有 `job_id`、`org_id`、`run_version`，业务状态仍以 PostgreSQL 为准。
4. [`internal/platform/taskqueue/asynq.go`](../internal/platform/taskqueue/asynq.go) 的 `handler`、`NewServer`：看任务类型校验、解析和重试策略。
5. [`internal/jobs/service.go`](../internal/jobs/service.go) 的 `Execute`：看领取租约、正文处理、索引、心跳和完成收尾。
6. [`internal/knowledge/service.go`](../internal/knowledge/service.go) 的 `Process`：看文件提取为正文并把文档置为 `READY`。
7. [`internal/rag/service.go`](../internal/rag/service.go) 的 `Index`：看分块、向量化和索引版本写入。

### 完整触发链

```text
Worker 启动
  → LoadWorker
  → Ping Redis
  → 启动 Asynq Server
  → 每 2 秒执行 jobs.Dispatch

Dispatch
  → 找 PENDING/RETRYING 且 next_run_at 到期的任务
  → 原子更新 dispatch_seq、next_dispatch_at
  → Enqueue(knowledge:ingest:v1)
  → 写回 last_dispatch_error

Asynq handler
  → 校验 TaskType 和 Payload
  → jobs.Execute
  → claim：校验 run_version、状态、租约和文档来源
  → documents.Get / Process
  → phase = INDEXING
  → indexer.Index
  → finish：SUCCEEDED、RETRYING、FAILED 或 CANCELED
```

### 为什么要有 `run_version`、`dispatch_seq` 和租约

- `run_version` 区分同一任务的不同运行轮次，旧消息不能执行新一轮任务。
- `dispatch_seq` 让同一轮的投递拥有唯一 Task ID，重复扫描不会无限生成重复消息。
- `lease_token` 和 `lease_until` 证明当前 Worker 仍拥有执行权；租约过期后，后续扫描会恢复任务，而迟到的 Worker 不能覆盖新状态。
- `HeartbeatInterval` 定期续租；`TaskTimeout` 限制一次执行总时长。

队列只传最小身份信息，不能把完整文档内容塞进 Redis。PostgreSQL 是任务执行状态的权威来源，Redis/Asynq 只是投递通道。

## 六、例四：知识库搜索和问答——同步 RAG 链路

### 阅读顺序

1. [`KnowledgeSearchView.vue`](../web/src/views/KnowledgeSearchView.vue) 或 [`AIConversationView.vue`](../web/src/views/AIConversationView.vue)：看用户输入如何发起搜索或问答。
2. [`web/src/lib/client.ts`](../web/src/lib/client.ts) 与 [`web/src/lib/ai-stream.ts`](../web/src/lib/ai-stream.ts)：普通请求看 `request`，流式回答看 `stream` 和 SSE 事件。
3. [`internal/rag/handler.go`](../internal/rag/handler.go) 的 `scope`、`readQuery`、`search`、`ask`：看身份、组织、查询规范化和输出。
4. [`internal/rag/service.go`](../internal/rag/service.go) 的 `Search`、`Ask`：看检索、来源复查和模型生成的编排。
5. [`internal/rag/retriever.go`](../internal/rag/retriever.go)：看问题向量化、有效索引过滤和召回。
6. [`internal/rag/index_repository.go`](../internal/rag/index_repository.go)：看 pgvector 查询和索引版本。
7. [`internal/platform/llm/`](../internal/platform/llm/)：看 Ollama/DeepSeek 的请求协议、超时和结构化结果校验。

```text
POST /knowledge/search
  → 校验 query/top_k
  → Embedder 生成问题向量
  → pgvector 召回有效片段
  → 复查组织和文档权限
  → 返回来源和分数

POST /knowledge/ask
  → 同样先检索并复查来源
  → Generator 根据片段生成回答
  → 再校验引用和来源
  → 返回答案
```

搜索/问答不是“拿到向量就直接交给模型”：组织授权、文档状态、索引版本、引用来源都属于链路依赖。修改检索阈值看 RAG 配置和 Service；修改模型请求看 `internal/platform/llm`；修改分块看知识库 chunker。

## 七、例五：AI 对话——HTTP 流式事件

### 阅读顺序

1. [`AIConversationView.vue`](../web/src/views/AIConversationView.vue)：看发送消息和确认工具动作的 UI 入口。
2. [`web/src/lib/client.ts`](../web/src/lib/client.ts) 的 `stream`：看请求超时、取消、SSE 内容类型和事件校验。
3. [`internal/ai/handler.go`](../internal/ai/handler.go) 的 `send`：看创建 SSE、启动对话轮次和处理断开。
4. [`internal/ai/runner.go`](../internal/ai/runner.go)：看模型调用、RAG、工具提案和消息事件。
5. [`internal/ai/sse.go`](../internal/ai/sse.go)：看服务端事件格式和结束信号。
6. [`internal/ai/store.go`](../internal/ai/store.go)：看对话、消息、工具动作和幂等请求如何持久化。

这里的事件是**连接内的 SSE 事件**，例如文本增量、工具提案、消息结束和错误；它和工单的持久化审计事件、Asynq 队列消息是三种不同机制。排查问题时先判断事件属于哪一类。

## 八、按“修改点”反查依赖

| 想修改什么 | 至少阅读这些位置 | 不要只改哪里 |
| --- | --- | --- |
| 按钮是否显示 | 对应 View、composable、后端 Handler/Service | 只改 Vue 权限判断 |
| 工单状态或领取 | ticket Handler、Service、Repository、事件查询 | 只改 SQL 前的 `if` |
| 上传限制 | 前端校验、knowledge Handler、Service、存储配置 | 只改前端大小提示 |
| 异步重试 | jobs 状态转换、`Dispatch`、队列重试、`Execute.finish` | 只改轮询间隔 |
| 文档索引 | knowledge.Process、jobs.Execute、rag.Index、Worker 入口 | 只改“索引”按钮 |
| RAG 答案 | Handler、retriever、Service、LLM 适配器、引用校验 | 只改 Prompt |
| AI 工具动作 | ai Handler、Runner、Store、相关业务 Service | 只改模型输出解析 |

## 九、一次完整学习检查清单

读完一个工作流后，尝试回答：

1. 第一个触发点是按钮、页面加载、定时器、HTTP 请求还是 Worker 扫描？
2. 路由是否经过 `RequireUser`？组织成员关系在哪里再次确认？
3. 哪个 Service 才是真正的业务规则入口？
4. 数据是同步写入，还是先写任务状态再异步执行？
5. 哪个条件阻止并发请求覆盖彼此的结果？
6. 业务变化和审计事件是否同事务提交？
7. 队列消息中传了什么，哪些内容仍必须从 PostgreSQL 读取？
8. 失败后是返回冲突、自动重试、人工重试，还是不可重试失败？
9. 前端显示的状态来自哪个 API，页面关闭后谁仍然继续工作？
10. 如果只改一个文件，是否会绕过后端权限、数据库约束或 Worker 状态机？

掌握这十个问题后，再开始修改功能；先画出触发链，再决定修改点，通常比直接从按钮代码开始改更安全。
