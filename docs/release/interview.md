# 十二个深入面试问题与参考回答

这些是 AI 按实际实现整理的复习答案。先自行回答，再对照代码和证据；不能将读过答案写成独立实现经验。

## 1. 为什么选择模块化单体，而不是拆微服务？

当前复杂度在授权、一致性和模型边界，单仓库 API 便于通过同一 PostgreSQL 事务保证工单与事件原子性。Worker 因耗时任务独立运行，但仍共享领域与存储约束。拆服务会增加网络失败、版本发布及跨服务事务成本；只有团队、扩容或独立生命周期需求成立后再拆。入口见 cmd/api/main.go、cmd/worker/main.go。

## 2. user 与 member 为什么分开？JWT 里放角色不就够了吗？

user 是全局身份，member 是 `(org_id,user_id)` 下的关系，角色和状态随组织变化。JWT 只确认用户身份，组织访问每次查 active 关系，避免旧 Token 保留过期权限。admin 在 A 组织不意味着在 B 有任何权利；数据库故障不能降级相信客户端角色。追问并发撤权：现实现不承诺所有并发请求与撤权完全线性化，且没有公开角色变更接口。

## 3. 两人同时领取一个工单，为什么不会都成功？

服务端检查当前组织权限，用带旧 version、OPEN、未指派条件的更新取得结果，再在同一事务写事件。只有一个更新能匹配；另一方收到冲突。前端按钮禁用只是减少重复点击，正确性靠数据库条件。看 ticket/service.go、claim_test.go 及真实并发集成测试；不承诺公平性或通用请求幂等。

## 4. 为什么编辑发生 409 后不自动重试？

重试需要新的业务决定：旧表单可能覆盖他人改动，旧指派候选也可能不再有效。前端保存打开表单时的 version，冲突后关闭意图、刷新，再请用户确认；若刷新失败要如实提示。删除沿用现有无 version 的管理员软删契约，以明确二次确认为 UI 防误触；不能说删除也有同样版本前置条件。

## 5. 用了 AbortController，为什么还要 epoch/作用域判断？

取消可能晚于响应完成，也无法保证服务器停止处理。组织、路由或会话变化后，旧响应即使返回也必须失效。作用域在提交 UI 状态和跳转前检查；删除的晚响应不能把新组织页面跳回旧组织。新增 management.spec 用延迟响应覆盖此类竞态，并在 403/404 时清保护内容。

## 6. Redis 已经有队列，为什么 PG 还要 knowledge_jobs？

PG 保存业务状态、投递意图、next_run_at、attempts 和运行版本；Redis 通知可重复或暂时丢失，不能成为唯一真相。Worker 领取租约后用 token、run_version、有效期和父对象检查保护最终写入。外部模型调用不能严格 exactly-once，但业务发布可通过条件与幂等检查收敛。

## 7. 索引写完、任务确认前进程崩溃，会发生什么？

等待真实租约过期后由恢复流程处理，旧 token 不能覆盖新执行；重试发现当前 hash、版本和索引已成功时收敛 SUCCEEDED，避免无意义的额外模型调用。第三次尝试的这一边界也有回归。W11 用实际 SIGKILL 和等待验证，没有手工改 DB 时间制造恢复。参见 failure-drills.md。

## 8. 文件保存和数据库写入能放进一个事务吗？

当前不能跨文件系统与 PG 做原子提交。文件使用私有随机键和不覆盖发布；明确失败可补偿，未知提交结果保留对象并记录 journal，避免误删已被数据库引用的数据。断电恢复和自动清理器没有完整实现，备份也要同时考虑数据库与对象。参见 ADR-0005 和知识库设计。

## 9. RAG 的“有引用”为什么不等于答案正确？

引用合法性检查组织、文档、偏移、版本与实际来源，能阻止伪造和跨组织引用；语义相关及陈述是否被原文支持还需要评测。W10 固定正负例、精确区间计算 Recall/MRR 等，AI 预标注待人工复核。W12 deterministic 模型只验证 HTTP/Worker/SSE/UI 链路，不能替代语义实验。

## 10. 混合检索是否就是 BM25 + ANN？为什么不是？

当前向量是 pgvector 精确余弦扫描；另一分支是英文标识符/汉字双字片段的参数化字面子串匹配，按命中词项排序，以 RRF 合并候选，不是 BM25，也没有 ANN 索引。固定小集中的提升不能保证大规模效果。数据增长后先量化延迟、召回与过滤行为，再比较 ANN/全文索引。

## 11. 如何防止模型越权创建工单或重复确认？

模型只有工具白名单，产生 pending action；人确认后服务端重新检查 owner、组织与 action 状态，在事务/约束下关联一次业务结果。重复点击返回已有结果或冲突，不让模型凭自然语言绕过确认。拒绝和超时均有明确状态。提示词注入是输入数据风险，不能把防护仅交给系统提示词。

## 12. 性能优化和故障策略怎样有证据？

先区分纯业务与模型耗时，固定数据、并发、预热、时长与源码，通过 profile 找缓存解码分配热点。最终微基准 B/op 下降约 42.5%，业务吞吐改善更小；发现重复 JSON 字段边界后补回归并重测，没有保留不安全的高增益结论。缓存故障可回源，AI 配额故障则保守拒绝：可用性选择取决于业务风险。指标仅进程内、无生产容量或跨机高可用承诺。
