## 1. 项目做什么

NexusDesk 面向企业内部的软件支持场景，将问题提交、任务领取、沟通、处理和结果记录集中到一个系统中。例如，业务人员发现报表异常，可以在所属组织创建工单；处理人员领取并推进问题，管理员确认关闭，后续通过评论和事件记录查看处理过程。

项目以 Go 后端工程实践为重点：既实现可操作的业务，也验证身份认证、组织隔离、数据库事务、状态约束和并发写入。长期方向是在工单系统上增加知识库、带来源引用的问答和受控工具调用；这些属于后续计划。

当前角色只有 `member` 和 `admin`。业务上可以由某些成员承担支持工作，但系统还没有独立的 `support` 角色。

## 3. 当前怎样使用

第一次使用自己的开发数据库，需要先通过 API 注册账号，再创建组织，或由管理员将该账号添加到已有组织。注册本身不会自动创建组织，也不会返回登录 Token。

准备好账号和组织后，网页中的主要流程是：

**登录 → 选择组织 → 创建工单 → 查看详情 → 领取 → 开始处理 → 评论沟通 → 标记解决 → 管理员关闭。**

使用普通浏览器窗口和无痕窗口登录两个不同成员，可以观察同一张工单的领取竞争。后端仅允许一个请求成功；另一个请求得到 `409`，页面刷新后显示最新受理人。

### 3.1 用户与组织成员的区别

`users` 表保存用户账号；`organization_members` 保存用户属于哪个组织、在该组织的角色和状态。一个账号可以属于多个组织，并在不同组织担任不同角色。

JWT 用于确认“请求者是谁”。“能否访问这个组织、能否执行这个动作”仍由后端根据数据库中的成员关系判断，客户端传来的用户 ID、角色或组织路径不能替代授权。

当前组织内的有效成员可以查看本组织全部未删除工单，并不限于自己创建的工单。不同组织之间隔离；非成员和已停用成员不能通过猜测 ID 访问目标组织资源。

### 3.2 工单状态与权限

| 操作 | 状态变化 | 主要条件 |
| --- | --- | --- |
| 领取 | OPEN 保持 OPEN | 当前用户是有效成员，工单未指派，版本匹配；受理人设为当前用户 |
| 开始处理 | OPEN → IN_PROGRESS | 已有有效受理人，由受理人本人或管理员操作 |
| 标记解决 | IN_PROGRESS → RESOLVED | 受理人仍有效，由受理人本人或管理员操作 |
| 关闭 | RESOLVED → CLOSED | 仅管理员 |
| 重新打开 | RESOLVED → IN_PROGRESS | 仅管理员，且已有有效受理人 |

**领取与开始处理是两个动作。** CLOSED 当前不能重新打开，也不能新增评论；已有评论和事件仍可在有权限时查询。完整规则见[状态机](ticket-state-machine.md)和[权限矩阵](authorization-matrix.md)。

## 4. 技术结构与核心设计

项目采用模块化单体：一个 Go API 服务，配合 PostgreSQL 和独立的 Vue 开发前端。

| 部分 | 当前采用的技术 | 作用 |
| --- | --- | --- |
| 后端 | Go 1.26.1、Gin、pgx/pgxpool | HTTP 路由、业务逻辑与数据库访问 |
| 数据库 | PostgreSQL 17、Goose | 数据持久化、约束、事务和增量迁移 |
| 身份认证 | Argon2id、JWT HS256 | 密码散列与短期访问凭据 |
| 前端 | Vue 3、TypeScript、Vue Router、Pinia、Vite | 页面、路由、会话状态与开发代理 |
| 验证 | Go 测试与 race、Vitest、Playwright | 单元、数据库、并发和浏览器验证 |
| 本地环境 | Docker Compose、Python 烟测脚本 | 启动数据库与复现隔离验收流程 |

依赖以 [go.mod](../go.mod) 和 [web/package.json](../web/package.json) 及各自锁定文件为准。

后端请求经过 `Handler → Service → Repository → PostgreSQL`。Handler 处理 HTTP 参数与响应；Service 判断权限、状态和事务边界；Repository 执行 SQL。受保护路由先经过认证中间件，组织资源还要检查成员资格。

当前六张业务表如下，另外还有 Goose 自己的迁移版本记录表：

| 表 | 保存的内容 |
| --- | --- |
| `users` | 账号、显示名和密码散列 |
| `organizations` | 组织 |
| `organization_members` | 用户与组织的关系、角色和状态 |
| `tickets` | 工单内容、组织、创建者、受理人、状态、版本和软删除标记 |
| `ticket_comments` | 工单讨论内容 |
| `ticket_events` | 操作者、事件类型、相关版本以及变更数据 |

### 4.1 当前值得介绍的工程能力

**组织隔离。** 工单、评论和事件的查询限定组织范围；成员权限来自数据库。页面隐藏按钮只改善交互，真正的授权在后端完成。

**事务一致性。** 工单修改与对应事件在同一个事务中提交。事件写入或提交失败时，业务变更回滚，避免只改工单却没有相应事件。

**原子领取。** 使用带组织、状态、未指派和版本条件的 `UPDATE … RETURNING` 完成领取。竞争失败不会覆盖成功者；成功后版本加一，并在同一事务写入一条领取事件。该设计已验证并发正确性，但没有宣称生产吞吐量、抢单公平性或请求级幂等。

**版本冲突处理。** 编辑、状态流转和领取提交 `expected_version`，防止旧页面覆盖新的数据。评论不递增工单版本。JavaScript 侧对 ID 和版本采用无损处理，避免大整数被静默舍入。

**前端请求与会话管理。** 切换组织、退出或开启新会话后，旧请求不能覆盖当前页面。Token 仅存在内存中，刷新页面需要重新登录；当前有效期为 15 分钟。网络故障提供重试提示，写操作不会被静默自动重发。

## 6. 当前本机运行情况与已解决的问题

本次对话已实际排查日常开发环境：数据库起初可以连接，但没有任何业务表，也没有迁移版本表。随后通过容器本地连接执行仓库现有六条迁移，数据库更新到版本 6；演示账号注册实际返回 `201`，登录实际返回 `200`。这次初始化发生在第四周归档验收之后，不能将历史周报中“仅使用隔离测试库”的记录理解为日常数据库当时也已经准备好。

编写本文时再次只读检查，`http://127.0.0.1:8080/healthz` 和 `http://127.0.0.1:5173/login` 均返回 `200`。这是当时的服务状态，不表示进程会在关机或关闭终端后持续运行。

| 遇到的现象 | 原因 | 当前处理或使用要求 |
| --- | --- | --- |
| 启动提示 `JWT_ISSUER is required` | Go 进程未获得该环境变量 | 本地配置需齐全，并在启动 Go 的同一终端导出；程序不自动读取 `.env` |
| 浏览器只有登录入口 | 前端尚无注册页面 | 通过注册 API 准备账号 |
| 直接请求注册 URL 返回 404 | 默认发出 GET，而注册只接受 POST | 使用 POST 和 JSON 请求体 |
| 正确 POST 注册返回 500 | 日常数据库尚未应用迁移，`users` 表不存在 | 已执行六条迁移并验证注册、登录成功 |
| 新账号没有组织可选 | 注册不自动建立组织成员关系 | 创建组织，或由该组织管理员添加账号 |

日常启动顺序为：**准备并导出本地配置 → 启动数据库 → 应用迁移 → 启动 Go API → 启动 Vue → 准备账号与组织 → 操作工单。** `/healthz` 是存活检查，不能用它判断业务表是否齐全。

配置与迁移的完整命令见 [README 运行说明](../README.md)。已有数据库迁移记录应通过 Goose 增量管理，不为排查问题直接删库、删卷或修改旧迁移。

## 9. 可用于阶段汇报的介绍

> NexusDesk 是一个面向企业内部软件支持场景的组织工单系统，采用 Go、Gin、PostgreSQL 和 Vue 3。当前已完成第四周本地 MVP，具备身份认证、组织成员权限、工单创建与处理、评论、事件记录及原子领取能力。后端共实现 17 个业务接口，业务修改与事件在同一事务中提交，并通过真实 PostgreSQL 验证了多人同时领取时只有一个请求成功。前端已经接入真实 API，可以演示登录、选择组织、建单、领取、处理与查看记录。注册和组织管理暂时通过 API 使用；知识库、AI 问答和公开部署仍属于后续工作。

汇报时可结合[第四周参考回答](weekly/week04-answers.md)说明自己对权限、事务和并发的理解。工程由 AI 按委托参与实现，应据实说明协作方式；独立讲解、修改和排查能力需要通过自己的操作继续验证。
